# UI Interview

UI의 생김새가 아니라 사용자의 행동 이후에 일어날 일을 빠르게 확정한다.

이 스킬의 성공은 질문 수가 많아서가 아니라, 구현 결과를 바꾸는 결정을 적은 질문으로
확보하는 데 있다. 사용자가 설명하기 귀찮아한다는 전제를 유지하고, 이미 알 수 있거나
일반적인 방식으로 안전하게 처리할 수 있는 내용은 다시 묻지 않는다.

## 실행 경계

이 스킬은 짧은 질의응답만 담당한다.

- 별도의 Figma, 스크린샷, 기획서 또는 화면 목록을 요청하지 않는다.
- 인터뷰를 시작하기 위해 전체 변경 파일, 관련 스펙 또는 기존 화면 흐름을 조사하지 않는다.
- 시각 디자인, 구현 기술, 컴포넌트 구조 또는 라이브러리 선택을 인터뷰하지 않는다.
- 제품 구현, 파일 수정, 테스트 또는 문서 갱신을 직접 수행하지 않는다.
- 프로젝트가 구현 단계에서 요구하는 스펙·코드·검증 확인을 생략하게 만들지 않는다.
  그 확인은 이 짧은 인터뷰가 끝난 뒤 원래 작업 절차에서 수행한다.

## 1. UI 작업 여부를 빠르게 판단한다

현재 요청과 이미 알려진 작업 맥락만으로 판단한다. 현재 브랜치명이 이미 보이면 보조
근거로 사용할 수 있다. 브랜치명이 필요하지만 보이지 않을 때만 브랜치 이름을 한 번
확인한다.

다음 중 하나가 명확하면 UI 작업으로 본다.

- 사용자가 화면이나 UI 구현을 요청했다.
- 현재 작업이 화면, 컴포넌트, 사용자 입력 또는 화면 이동을 다룬다.
- 사용자가 `계속 구현해줘`처럼 대상을 생략했지만, 현재 브랜치나 티켓 설명으로 지금 이어서
  수행할 작업이 UI 구현임을 알 수 있다.

UI 작업인지 애매할 때만 다음처럼 한 문장으로 확인한다.

```text
지금 작업은 <화면 또는 요소>의 UI 구현으로 이해하면 될까요?
```

UI 작업이 명확하면 이 확인도 생략한다. 순수 스타일 변경이거나 상호작용이 이미 모두
정해져 있으면 질문 없이 원래 작업으로 돌아간다.

## 2. 구현 결과를 바꾸는 빈칸 하나를 고른다

현재 요청과 대화에서 아직 답이 없고, 답에 따라 사용자가 겪는 동작이 달라지는 항목만
고른다. 우선순위는 다음과 같다.

1. 사용자가 요소를 눌렀거나 입력을 마친 뒤 무엇을 보게 되는가
2. 다른 화면으로 이동한다면 어디로 가는가
3. 취소하거나 뒤로 갔을 때 무엇이 유지되거나 사라지는가
4. 로그인, 권한, 입력 완료처럼 동작을 제한하는 조건이 있는가
5. 실패했을 때 사용자가 반드시 알아야 하거나 선택해야 하는 동작이 있는가

다음은 묻지 않는다.

- 코드나 앞선 대화에서 이미 확인된 내용
- 색상, 간격, 크기, 글꼴 등 정해진 시각 디자인
- 구현 결과에 영향을 주지 않는 사소한 선호
- 아직 요구되지 않은 확장 기능과 예외 상황
- 개발자가 일반적인 방식으로 안전하게 처리할 수 있는 세부 구현

질문할 빈칸이 없으면 인터뷰를 시작하지 않는다.

## 3. 한 번에 질문 하나만 한다

먼저 필요한 경우에만 지금까지 확정된 내용을 한 문장으로 짚고, 가장 중요한 질문 하나를
한다.

```text
현재 이해: <이미 확정된 내용을 한 문장으로 요약>

질문: <사용자가 실제로 보게 되는 결과를 묻는 한 문장>

- <선택지>
- <선택지>
- <필요할 때만 세 번째 선택지>
- 직접 설명
```

현재 이해를 반복할 필요가 없으면 생략한다. 선택지는 보통 두세 개만 제시하고 서로 다른
사용자 경험을 설명한다. 사용자의 생각을 제한할 수 있으므로 선택지가 네 개 이상 필요하면
질문을 더 작은 결정으로 나눈다.

안전하고 흔한 선택이 있으면 첫 번째 선택지에 다음처럼 짧게 이유를 덧붙일 수 있다.

```text
- 입력 내용을 유지한 채 취소 여부를 확인한다. (권장: 실수로 내용을 잃지 않음)
```

데이터 삭제, 결제, 외부 공개, 권한 또는 되돌리기 어려운 결과에는 임의의 추천을 붙이거나
사용자 대신 결정하지 않는다.

## 4. 사람에게 보이는 결과로 말한다

질문과 선택지에서는 기술 용어만 제시하지 않는다. 사용자가 화면에서 무엇을 보고 무엇을
할 수 있는지를 먼저 설명한다.

| 피할 표현 | 사용할 표현 |
| --- | --- |
| 모달을 띄우나요? | 지금 화면 위에 확인창을 띄우나요? |
| 바텀시트인가요? | 화면 아래에서 선택 목록이 올라오게 하나요? |
| 상세로 라우팅하나요? | 해당 항목의 자세한 내용을 보여주는 화면으로 이동하나요? |
| 토스트를 표시하나요? | 작업이 끝났다는 짧은 안내를 잠시 보여주나요? |
| dismiss하나요? | 안내창을 닫고 지금 보던 화면에 그대로 머무르나요? |
| toggle인가요? | 누를 때마다 켜짐과 꺼짐 상태가 바뀌나요? |
| debounce가 필요한가요? | 빠르게 여러 번 눌러도 한 번만 처리해야 하나요? |
| optimistic update인가요? | 먼저 화면에 반영하고, 실패하면 원래 상태로 되돌리나요? |

사용자가 먼저 사용한 용어는 그대로 쓸 수 있다. 기술 용어가 정확성을 위해 필요하면 쉬운
설명 뒤에 괄호로 한 번만 덧붙인다.

좋은 질문:

```text
작성 버튼을 누르면 어떤 방식으로 작성을 시작하나요?

- 작성 내용을 입력하는 새 화면으로 이동한다.
- 지금 화면 위에 작은 작성창을 띄운다.
- 화면 아래에서 작성 종류를 먼저 고르게 한다.
- 직접 설명
```

피해야 할 질문:

```text
작성 버튼은 모달, 바텀시트, 라우팅 중 무엇으로 처리할까요?
```

## 5. 답변마다 다음 질문의 필요성을 다시 판단한다

사용자 답변을 현재 이해에 반영한 뒤, 남은 빈칸이 실제 구현을 막는지 다시 판단한다.

- 기본 목표는 전체 1~3개 질문이다.
- 구현 결과를 크게 바꾸는 결정이 남았을 때만 최대 5개까지 질문한다.
- 정해진 개수를 채우기 위해 질문하지 않는다.
- 사용자가 `일반적으로`, `알아서`, `보통 방식으로` 처리해 달라고 하면 안전한 일반 동작을
  선택하고 더 묻지 않는다.
- 단, 데이터 삭제, 결제, 외부 공개, 권한 또는 되돌리기 어려운 결과는 `알아서`라는 표현만으로
  결정하지 않는다. 사용자 경험을 바꾸는 선택지를 사람 친화적으로 한 번 질문한다.
- 일반 동작을 선택했으면 최종 요약에서 어떤 동작을 적용하는지 밝힌다.

사용자의 답이 다른 미결정 사항까지 함께 해결했다면 다음 질문을 생략한다.

일반적인 입력 제출에서 사용자가 세부 처리를 맡겼다면 다음 안전한 동작을 적용할 수 있다.

- 처리 중에는 같은 요청이 여러 번 실행되지 않도록 실행 요소를 잠시 누를 수 없게 한다.
- 처리에 실패하면 사용자가 입력한 내용을 유지하고 실패 안내와 다시 시도할 방법을 제공한다.

이 기본 동작은 삭제, 결제, 외부 공개, 권한 요청에는 적용하지 않는다.

## 6. 결정이 확보되면 즉시 끝낸다

별도 문서나 긴 보고서를 만들지 않는다. 확정한 동작과 AI가 적용하기로 한 일반 동작만
짧게 구분한다.

```text
다음과 같이 이해했습니다.

확정된 동작
- <사용자가 직접 정한 동작>

일반적인 방식으로 적용할 동작
- <AI가 선택한 안전한 일반 동작>

이 기준으로 구현을 계속하면 됩니다.
```

두 번째 구분에 내용이 없으면 생략한다. 기술 용어는 구현자에게 유용할 때만 쉬운 설명 뒤에
덧붙일 수 있다.

## 종료 기준

다음 중 하나이면 종료한다.

- 구현 결과를 바꾸는 미결정 사항이 더 없다.
- 사용자가 일반적인 방식으로 남은 세부 동작을 처리해 달라고 했다.
- 질문이 스킬의 최대 범위인 5개에 도달했다.

5개 질문 뒤에도 중요한 결정이 남으면 확인된 내용과 남은 결정 하나를 간단히 알리고 원래
작업 흐름으로 돌아간다. 사소한 선호까지 모두 확정하려고 인터뷰를 늘리지 않는다.
