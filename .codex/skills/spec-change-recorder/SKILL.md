# Spec Change Recorder

공식 스펙과 현재 작업의 차이를 근거로 분류하고, 실제 스펙 변경이 필요한 경우에만 검토 가능한 변경 제안을 남긴다.
변경 제안이 승인된 공식 결정처럼 사용되는 일을 막기 위해 이 Skill은 공식 스펙을 수정하지 않는다.

## 변경 범위

이 Skill이 수정할 수 있는 대상은 다음으로 제한한다.

- 새 변경 제안: `docs/spec-changes/pending/*.md`
- 같은 변경을 다루는 기존 제안이 있을 때: 해당 `pending` 파일

다음 대상은 수정하지 않는다.

- `docs/specs/`의 공식 스펙과 색인
- `docs/spec-changes/applied/`
- 소스 코드, 테스트, 빌드 설정
- 승인 여부와 반영 커밋처럼 확인되지 않은 정보

이 Skill을 호출한 상위 작업이 소스 코드를 수정하는 것은 별개다. 이 Skill 자체는 차이 판정과 변경 제안 기록에만 집중한다.

## 1. 필요한 스펙만 찾기

1. 현재 요청, 작업 중인 파일과 변경 Diff를 확인한다.
2. `docs/specs/INDEX.md`만 먼저 읽고 관련 스펙 ID와 공통 계약을 찾는다.
3. 관련 스펙의 `AI 작업 컨텍스트`를 먼저 읽는다.
4. 차이를 판정하기에 정보가 부족할 때만 해당 스펙의 나머지 본문을 읽는다.
5. 직접 관련된 `COMMON.md`, `contracts/API.md`,
   `contracts/DATA_MODEL.md`, `UI_AND_NAVIGATION.md`만 추가로 읽는다.
6. `INDEX.md`에 매핑이 없으면 `COVERAGE.md`에서 원본 ID나 이름의 반영
   위치를 확인한다. 전체 반영 상태나 매핑 누락을 조사할 때가 아니면
   `COVERAGE.md`를 읽지 않는다.
7. `COVERAGE.md`에도 매핑이 없으면 `docs/specs/` 안에서 현재 기능명과
   코드 경로로 범위를 제한해 검색한다.

모든 스펙을 한 번에 읽지 않는다. 같은 세션에서 변경되지 않은 문서도 반복해서 읽지 않는다.
로컬 공식 스펙이 존재하면 일반 구현 판정을 위해 Notion 접근을 요구하지 않는다.

## 2. 차이 분류하기

근거를 확인한 뒤 다음 중 하나로 분류한다.

### `IMPLEMENTATION_GAP`

공식 스펙의 목표 동작은 그대로지만 코드가 아직 구현하지 못했거나 잘못 구현한 경우다.

- 변경 제안을 만들지 않는다.
- 상위 작업에 코드 또는 테스트를 공식 스펙에 맞춰야 한다고 알린다.

### `SPEC_CHANGE`

새 요구사항이나 확인된 제약으로 인해 공식 목표 동작 자체가 달라져야 하는 경우다.

- 중복 여부를 확인한 뒤 `pending` 변경 제안을 작성한다.
- 승인 전에는 제안 내용을 공식 개발 기준으로 사용하지 않는다.

### `SPEC_GAP_OR_CONFLICT`

필요한 스펙이 없거나, 표현이 모호하거나, 둘 이상의 공식 문서가 서로 충돌하는 경우다.

- 확인된 사실과 해결해야 할 질문을 구분해 변경 제안을 작성한다.
- 어느 쪽이 정답인지 추측해서 확정하지 않는다.
- 결과를 크게 바꿀 수 있으면 상위 작업을 진행하지 말고 사용자에게 확인을 요청한다.
- 충돌이 API, DB, 인증·권한 또는 공용 데이터 계약을 포함하면 이 분류보다
  `SHARED_CONTRACT_CHANGE`를 우선 적용한다.

### `SHARED_CONTRACT_CHANGE`

API, DB, 인증·권한, 공용 데이터 구조 또는 여러 작업자가 함께 의존하는 계약이 달라져야 하는 경우다.

- 변경 제안을 작성하고 `차단 변경`임을 명시한다.
- 사용자에게 즉시 알린다.
- 승인 전에는 변경된 계약에 의존하는 구현을 진행하지 않는다.

## 3. 중복 확인하기

새 파일을 만들기 전에 `docs/spec-changes/pending/`과 `docs/spec-changes/applied/`에서 다음 항목을 검색한다.

- 영향받는 스펙 ID 또는 계약 ID
- 관련 Jira 작업
- 동일한 기존 내용과 변경 내용
- 같은 기능명과 핵심 용어

처리 기준:

- 같은 결론을 다루는 `pending` 제안이 있으면 새 파일을 만들지 않고 확인된 근거만 기존 파일에 보강한다.
- 이미 `applied`에 같은 변경이 있으면 공식 스펙의 반영 여부를 보고하고 새 제안을 만들지 않는다.
- 같은 스펙을 다루더라도 변경 목표가 다르면 별도 제안을 작성하고 관련 제안 링크를 남긴다.

## 4. 변경 제안 작성하기

`docs/spec-changes/TEMPLATE.md`의 구조를 사용한다.

파일명:

- Jira 작업이 있으면 `CHG-<Jira키>-<짧은-영문-제목>.md`
- Jira 작업이 없으면 `CHG-<YYYYMMDD>-<작성자>-<짧은-영문-제목>.md`
- 작성자를 확인할 수 없으면 추측하지 말고 `unknown`을 사용한다.
- 같은 파일명이 존재하면 내용을 덮어쓰지 말고 충돌하지 않는 짧은 식별자를 추가한다.

내용 작성 규칙:

- `기존 내용`에는 공식 스펙의 실제 문구나 의미를 출처 경로와 제목을 포함해 적는다.
- `제안 내용`에는 제안하는 목표 동작을 검증 가능한 문장으로 적는다.
- `변경 근거`에는 코드 경로, 테스트 결과, 사용자 결정 또는 확인된 제약 등 실제 근거를 적는다.
- `확인된 영향`에는 확인된 영역만 적고 추측은 `확인 필요`로 표시한다.
- `상태`는 `제안`으로 둔다.
- 결정, 결정자, 결정일, 반영 문서와 반영 커밋은 확인 전까지 비워 둔다.
- 공용 계약 변경이면 `차단 변경: 예`로 기록한다.
- 모호성이나 충돌이면 `## 확인이 필요한 질문`을 추가한다.
- 사용자가 승인되지 않은 변경을 공식 스펙에 바로 반영해 달라고 요청해도
  이 Skill은 공식 스펙을 수정하지 않고 제안만 기록한다.

## 5. 결과 확인하기

작성 또는 보강 후 파일을 다시 읽고 다음을 확인한다.

- 공식 스펙과 제안 내용이 명확히 구분되어 있다.
- 영향 스펙이나 계약 ID와 근거 경로가 기록되어 있다.
- 승인되지 않은 결정을 확정적으로 표현하지 않았다.
- 기존 제안과 불필요하게 중복되지 않는다.
- 공식 스펙과 `applied` 파일은 변경되지 않았다.

## 6. 상위 작업에 보고하기

다음 형식으로 간결하게 보고한다.

```text
분류: IMPLEMENTATION_GAP | SPEC_CHANGE | SPEC_GAP_OR_CONFLICT | SHARED_CONTRACT_CHANGE
변경 제안: 생성 경로 | 보강 경로 | 생성하지 않음
근거: 확인한 스펙과 코드 또는 결정
작업 차단: 예 | 아니오
다음 조치: 코드 수정 | 팀 승인 대기 | 사용자 확인 필요
```
