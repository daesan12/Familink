# KDT Retrospective Capture

작업 흐름을 방해하지 않으면서 나중에 KPT 또는 Lessons Learned로 다듬을 가치가 있는 사건만
개인 로컬 메모에 남긴다. 좋은 기록은 단순히 "무엇을 했다"가 아니라 개발자가 나중에 다음
질문에 답할 수 있게 한다.

- 어떤 신호 때문에 문제나 개선 기회를 알아챘는가?
- 어떤 가설과 시도를 거쳐 원인을 좁혔는가?
- 무엇을 바꿨고 어떤 검증으로 해결을 확인했는가?
- 다음에 비슷한 조건이 나타나면 무엇을 먼저 확인하거나 반복해야 하는가?

이 기록은 공식 문서가 아니라 후보 자료이므로 짧고 사실 중심이어야 한다.

## 실행 경계

이 스킬은 다음 결과만 만든다.

1. 현재 작업자를 안전하게 식별한다.
2. 방금 발생한 사건이 회고 기준을 충족하는지 판단한다.
3. 민감정보와 사람에 대한 평가를 제거한다.
4. 한국 시간 기준 개인별 날짜 파일에 한 항목을 생성하거나 보완한다.
5. 대상 파일이 Git에서 제외되는지 확인한다.

Jira, Notion, Confluence, 공식 스펙, 제품 코드, Git 이력은 수정하지 않는다. 회고 메모를 stage,
commit 또는 push하지 않는다. 최종 KPT 반영은 사람이 선별하는 별도 작업이다.

## 2. 개발자 관점에서 회고 가치 판정

아래 세 질문에 모두 `예`라고 답할 수 있을 때 기록한다.

1. **사실성**: 오류, 코드, 스펙, 테스트 결과처럼 직접 확인한 근거가 있는가?
2. **영향성**: 품질, 일정, 재작업, 운영 위험 또는 팀의 판단에 실제 영향을 주었는가?
3. **재사용성**: 비슷한 조건의 다음 개발 작업에서 적용할 판단 기준이나 행동이 있는가?

다음 사건은 세 기준을 충족할 가능성이 높다.

- **Keep**: 품질이나 속도를 실제로 높였고 다음 작업에서도 반복할 만한 방법
- **Problem**: 예상하지 못한 실패, 잘못된 가정, 누락된 계약, 반복될 가능성이 있는 장애
- **Try**: 위 문제를 다음 작업에서 예방할 수 있는 구체적이고 실행 가능한 변화
- **Learned**: 문서나 코드만 훑어서는 알기 어려웠던 기술·도구·프로세스의 재사용 가능한 교훈
- 여러 접근 중 하나를 선택했고, 실제 제약과 검증 결과로 선택 이유를 설명할 수 있는 경우
- 테스트, 빌드, 정적 분석, 리뷰가 실제 결함이나 잘못된 전제를 발견한 경우
- 스펙과 구현, 도구 설명과 실제 환경, 담당 경계 사이의 충돌을 확인한 경우
- 실패한 접근이 원인을 좁히거나 이후의 판단 순서를 바꾼 경우
- 동일한 실수를 두 번 이상 겪어 재발 방지 규칙을 마련한 경우

해결되지 않은 문제도 영향이 크고 다음 진단에 도움이 된다면 기록할 수 있다. 이때 관찰된 증상과
이미 배제한 가설만 사실로 쓰고, 원인은 `미확인`으로 표시하며 다음 확인 행동을 남긴다.

다음은 기록하지 않는다.

- 파일 읽기, 검색, 정상 빌드처럼 일상적인 작업 진행
- 아직 원인이 확인되지 않은 추측이나 임시 가설
- 사용자에게 이미 단순 상태 보고로 충분한 내용
- 결과에 영향을 주지 않은 사소한 명령 오타
- 변경 파일과 실행 명령만 나열한 작업 일지
- `테스트를 추가하자`, `문서를 잘 읽자`처럼 적용 조건과 행동이 불명확한 교훈
- 검증 없이 성공했다고 판단한 해결책
- 개인 성과 평가, 책임 추궁, 감정적 표현

판단이 애매하면 기록하지 않는다. 회고 후보 수보다 신호의 품질을 우선한다.

## 3. 사건을 개발 흐름으로 재구성

기록 전에 사건을 다음 순서로 정리한다. 모든 시도를 나열하지 말고 원인 파악이나 의사결정에
영향을 준 시도만 남긴다.

1. **맥락과 기대**: 어떤 작업에서 무엇이 정상이어야 했는가?
2. **신호와 영향**: 실제로 무엇이 달랐고 개발 결과에 어떤 위험이나 재작업을 만들었는가?
3. **가설과 시도**: 무엇을 의심했고 어떤 결과로 채택하거나 배제했는가?
4. **원인 또는 판단 근거**: 확인된 근본 원인은 무엇인가? 설계 결정이라면 어떤 제약이 선택을
   갈랐는가?
5. **해결과 검증**: 무엇을 바꿨고 어떤 테스트·빌드·재현으로 결과를 확인했는가?
6. **일반화**: 비슷한 조건에서 먼저 확인할 신호, 적용할 순서 또는 피할 접근은 무엇인가?

관찰한 사실과 해석을 분리한다. 시간 절약이나 결함 감소 같은 효과를 수치로 쓰려면 실제 측정값이
있어야 한다. 측정하지 않았다면 수치를 만들어내지 않는다.

## 4. 안전하게 요약

기록 전 다음 내용을 제거하거나 일반화한다.

- 토큰, 비밀번호, 쿠키, 개인키, `.env` 값과 내부 접속 정보
- 실사용자 개인정보와 테스트에 불필요한 이메일
- 팀원에 대한 평가나 비난
- 확인되지 않은 원인과 과장된 성과

명령이나 오류가 근거로 필요하면 비밀값을 `[REDACTED]`로 바꾸고 핵심 한 줄만 남긴다.
사람이 아니라 조건, 과정, 시스템 동작을 주어로 쓴다.

## 5. 날짜 파일에 기록

한국 시간 `Asia/Seoul`의 오늘 날짜를 `YYYY-MM-DD`로 구한다. 대상은
`kdt-retrospectives/<작업자>/YYYY-MM-DD.md`이다. 작업자 디렉터리가 없으면 생성한다.

파일이 없으면 다음 머리말로 시작한다.

```markdown
# YYYY-MM-DD KDT 회고 후보

> 자동 수집된 개인 로컬 메모입니다. 최종 회고 반영 전 사실과 표현을 다시 검토합니다.
```

각 사건은 다음 형식을 사용한다.

```markdown
## HH:mm · [Keep|Problem|Try|Learned] 짧은 제목

- 작업: `Jira 키 또는 브랜치`, 없으면 `일반 작업`
- 맥락: 기대한 동작과 작업 범위
- 신호·영향: 관찰된 차이와 개발 결과에 미친 영향
- 가설·시도: 원인을 좁히거나 결정을 바꾼 시도와 결과, 없으면 `없음`
- 원인·판단: 확인된 원인 또는 선택을 가른 제약, 미해결이면 `미확인`
- 해결·검증: 적용한 변경과 이를 확인한 테스트·빌드·재현 결과
- 배운 점: `비슷한 조건에서는 A를 먼저 확인한 뒤 B한다`처럼 적용 조건과 행동을 함께 쓴 교훈
- 다음 행동: 코드·테스트·체크리스트·작업 순서에 반영할 구체적인 행동, 없으면 `없음`
- 근거: 파일 경로, 테스트명, 명령 결과 또는 오류의 비밀 제거 요약
```

한 사건이 여러 범주에 걸치면 가장 핵심적인 범주 하나를 제목에 사용하고 나머지는 본문에 녹인다.
제목은 결과를 드러내며 `문제 발생`, `작업 완료`처럼 모호하게 쓰지 않는다.

각 필드는 한두 문장으로 제한한다. `가설·시도`가 길어지면 최종 원인을 찾는 데 기여한 시도만
남긴다. `배운 점`은 해당 사건의 요약을 반복하지 말고 다른 작업에 적용 가능한 판단 규칙으로 쓴다.

## 6. 중복을 방지하고 기존 메모를 보완

쓰기 전에 오늘 파일을 읽는다.

- 같은 작업이 아니더라도 같은 원인·같은 판단 규칙·같은 다음 행동이면 새 항목을 추가하지 않는다.
- 기존 항목이 가설이고 이후 원인이 확인되었다면 해당 항목만 최소 수정한다.
- 한 작업에서 연속된 증상과 해결은 가능한 한 하나의 사건으로 합친다.
- 서로 독립적인 교훈만 별도 항목으로 분리한다.
- 기존 교훈이 너무 추상적이고 새 사건에서 적용 조건이 확인되었다면 새 항목 대신 기존 항목을
  구체화한다.

자동 수집 때문에 작업마다 한 줄씩 쌓이는 로그가 되지 않도록 한다.

## 7. Git 제외 검증

기록 후 다음과 동등한 읽기 전용 검사를 수행한다.

```powershell
git check-ignore -v -- "kdt-retrospectives/<작업자>/YYYY-MM-DD.md"
git status --short -- "kdt-retrospectives/"
```

첫 검사는 `.gitignore` 규칙을 보여야 하고 두 번째 검사는 아무 항목도 보여서는 안 된다.
검증에 실패하면 추가 기록을 중단하고 사용자에게 경로가 Git에 노출될 수 있다고 알린다.

## 작업 종료 시 동작

작업 도중 기준을 충족한 사건이 생기면 해결과 검증이 끝난 시점에 기록한다. 해결되지 않았지만
영향이 큰 장애는 작업을 넘기기 직전에 확인된 사실, 배제한 가설, 다음 진단 행동만 기록한다.
작업 종료 전에는 누락된 후보가 있는지 한 번만 점검한다. 기록할 사건이 없으면 파일을 만들지
않고, 회고가 없다는 사실도 별도 보고하지 않는다.

기록한 경우 최종 응답에는 개인 로컬 회고 후보를 몇 건 남겼는지만 짧게 알린다. 내용 전체를
반복하지 않는다.
