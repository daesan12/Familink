# [GROUPS_AND_MEMBERSHIP] 그룹·멤버십

> 상태: 일부 확정
> 기준: 2026-07-28, 최신 확정 Notion·활성 API 명세·최신 ERD

## AI 작업 컨텍스트

- 목적: 가족 그룹을 만들고 초대 코드와 가입 요청을 통해 구성원을 관리한다.
- 포함 범위: 그룹 생성·조회·전환, 가입 요청·승인·거절, 역할·별명, 관리자 권한, 탈퇴·삭제.
- 제외 범위: 그룹 구성원 프로필 팝업의 시각·상호작용 세부는 확정하지
  않는다.
- 핵심 규칙: 초대 코드를 통한 가입 요청만 사용하며, 관리자가 승인 시 보호자 또는 피보호자 역할을 지정한다. 관리자 여부는 구성원 역할과 별개다.
- 완료 조건: 그룹과 멤버십 관련 구현이 이 문서와 [API 계약](../contracts/API.md)의 API-GROUPS·API-ALIASES 항목을 만족한다.

## 확정된 동작

1. 로그인한 사용자는 본인의 그룹 역할을 선택해 그룹을 생성하며, 생성자는 그 그룹의 관리자가 된다.
2. 승인된 모든 그룹원은 6자리 초대 코드를 조회해 전달할 수 있다. 사용자를 ID로 검색하거나 ID로 직접 초대하지 않는다.
3. 사용자가 초대 코드를 입력하면 `PENDING_ADMIN` 가입 요청을 만든다. 이 요청 알림은 해당 그룹 관리자에게만 전달한다.
4. 관리자는 대기 중인 가입 요청을 승인하거나 거절하고, 승인 시 신청자의 보호자 또는 피보호자 역할을 지정한다.
5. 관리자는 활성 구성원의 역할을 변경한다. 변경된 권한은 즉시 적용하고 대상 사용자에게 결과를 표시한다.
6. 구성원의 개인화 호칭은 설정자·대상자·그룹 조합으로 저장한다. 설정 전에는 실제 이름을 표시하고, 변경 호칭은 설정자에게 보이는 해당 그룹의 화면과 알림 문구에만 적용한다.
7. 사용자는 자신이 속한 그룹을 조회하고 현재 화면의 그룹명 토글에서 현재 그룹을 전환할 수 있다.
8. 보호자 또는 피보호자가 0명이어도 그룹을 `PENDING`, `READ_ONLY` 또는 비활성으로 전환하지 않고 기능을 계속 제공한다.
9. 활성 그룹이 없는 사용자는 그룹 생성·참가와 본인의 가입 요청 대기 상태를 확인한다. 활성 그룹이 있는 사용자의 다른 그룹 가입 요청 결과는 앱 내부 알림으로 표시한다.
10. 사용자는 그룹에서 탈퇴할 수 있으며, 관리자가 다른 구성원이 있는 그룹에서 나가려면 먼저 관리자를 위임한다.
11. 관리자가 혼자인 그룹에서 나가기를 선택하면 그룹 삭제 확인으로 연결한다. 다른 활성 구성원이 있는 그룹은 삭제할 수 없다.
12. 그룹 탈퇴 구성원은 `left_at`으로 기록을 남기고 다시 가입할 때 기존 멤버십 행을 재활성화할 수 있다.
13. 보호자는 여러 활성 그룹에 참여할 수 있고 현재 화면의 그룹명 토글로
    그룹을 전환한다. 피보호자는 동시에 하나의 활성 그룹에만 참여할 수 있다.
14. 같은 그룹의 활성 구성원은 대상 구성원의 `memberId`, 조회자 기준
    `displayName`, 만 나이 `age`, `gender`로 구성된 축소 프로필을 조회한다.

확정된 예외:

- 조건: 관리자가 아닌 사용자가 가입 승인·거절·역할 변경·멤버 삭제·그룹 삭제를 요청한다.
  - 처리: 권한을 거부한다. 구체적인 응답은 [API 계약](../contracts/API.md)을 따른다.
- 조건: 동일 그룹과 동일 사용자 조합의 멤버십이 이미 존재한다.
  - 처리: 기존 멤버십을 중복 생성하지 않는다.
- 조건: 그룹을 삭제한다.
  - 처리: 관리자가 실행하며 다른 활성 구성원 존재 여부 등 ERD 제약조건을 만족해야 한다.
- 조건: 역할 변경 또는 구성원 이탈로 보호자나 피보호자가 0명이 된다.
  - 처리: 유예기간이나 상태 전환을 시작하지 않고 그룹을 계속 정상 이용한다.

## 구현 규칙

- 권한: 활성 그룹 구성원은 그룹 정보를 조회할 수 있다. 관리자는 가입 요청·역할·구성원·그룹 수명주기 작업을 수행한다. 본인 탈퇴는 본인 요청으로만 수행한다.
- 상태와 전이: 가입 요청은 `PENDING_ADMIN`에서 `APPROVED` 또는
  `REJECTED`로 전이한다. 멤버십은 활성 상태에서 탈퇴 시 `left_at`을
  기록하고, 재가입 시 기존 행을 재활성화한다.
- 가입 요청 처리: 요청 명령은 `decision=APPROVE|REJECT`를 사용한다.
  `APPROVE`이면 `assignedRole`이 필수이며 승인 상태와 처리 시각을 기록하고
  멤버십을 생성하거나 재활성화한다. `REJECT`이면 요청 상태를
  `REJECTED`로 바꾸고 처리 시각을 기록하되 `assigned_role`은 `NULL`로
  유지하며 멤버십은 생성하거나 변경하지 않는다.
- API:
  - 처리 주체: 그룹·멤버십·가입 요청·별명은 Spring Boot가 처리한다.
  - Method와 Path: `API-GROUPS-001~015`, `API-ALIASES-001`을
    [API 계약](../contracts/API.md)에서 참조한다.
  - 핵심 입력·결과: 그룹 정보, 초대 코드, 가입 요청 역할, 관리자 승인·거절·역할 변경·탈퇴·삭제 결과를 API 계약에 정의된 형식으로 주고받는다.
- 데이터:
  - 관련 엔티티: `family_groups`, `group_members`, `group_join_requests`, `member_aliases`.
  - 읽기·쓰기 소유자: Spring Boot가 이 도메인의 API와 관련 데이터의 모든 읽기·쓰기를 처리한다.
  - 주요 제약조건: 그룹 초대 코드·멤버십·대기 가입 요청·활성 관리자/돌봄 대상자 제약은 [DATA_MODEL](../contracts/DATA_MODEL.md)을 기준으로 적용한다.
- 화면:
  - 진입점: 그룹 없음, 그룹 생성, 초대 코드 입력, 가입 요청 대기, 그룹 정보·멤버 관리, 그룹 전환.
  - 사용자에게 표시할 결과: 현재 그룹, 요청 상태, 구성원 역할·별명과 관리자 작업 결과를 표시한다.
  - 모바일 화면은 React Native로 구현한다.

## 인수 조건

### AC-001

- Given: 로그인한 사용자가 그룹 생성 정보를 입력한다.
- When: 그룹 생성을 요청한다.
- Then: 새 그룹과 해당 사용자의 관리자 멤버십이 생성된다.

### AC-002

- Given: 사용자가 유효한 초대 코드로 가입을 요청한다.
- When: 가입 요청을 제출한다.
- Then: 요청은 `PENDING_ADMIN`으로 생성되고 해당 그룹 관리자에게만 알림이 전달되며, 승인 전에는 활성 멤버가 되지 않는다.

### AC-003

- Given: 관리자가 대기 중인 가입 요청을 확인한다.
- When: 승인 또는 거절을 선택한다.
- Then: 요청과 멤버십 상태가 선택한 결과에 맞게 변경된다.

### AC-004

- Given: 활성 구성원이 본인 그룹에서 탈퇴한다.
- When: 탈퇴를 요청한다.
- Then: 멤버십 이력이 보존된 채 비활성 상태가 된다.

## 미결정 사항

- 그룹 생성·가입 시 역할 선택의 세부 UI.
- 관리자 변경 확인·되돌리기 대상과 시점.
- 그룹 삭제의 사용자 확인·복구 정책 및 모든 외래키 처리 방식.
- 다중 그룹 게시글 작성·대상 그룹 선택의 최종 규칙.
