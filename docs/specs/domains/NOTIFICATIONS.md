# [NOTIFICATIONS] 앱·푸시 알림

> 상태: 일부 확정
> 기준: 2026-07-31, 최신 Notion API·ERD·Spring Boot 단일 백엔드 결정과 승인된 도메인 이벤트 알림 계약

## AI 작업 컨텍스트

- 목적: 서비스의 내부 알림을 제공하고, 사용자가 푸시 알림 종류별 수신 여부와 기기 토큰을 관리할 수 있게 한다.
- 포함 범위: 앱 내부 알림 목록·읽음 처리, 푸시 설정 7개, 기기 토큰 등록·해제, 알림 발생 대상·중복 방지, Android Firebase 푸시 전달.
- 제외 범위: 푸시 재시도·전송 이력·범용 outbox·메시지 브로커와 화면·레이아웃 구현.
- 핵심 규칙: 내부 알림 저장과 푸시 전달은 분리한다. 내부 알림은 이벤트 대상자에게 생성하고, 푸시는 해당 설정이 활성화되어 있으며 활성 기기 토큰이 있을 때만 보낸다.
- 완료 조건: 알림 동작은 이 문서와 [API 계약](../contracts/API.md)의 NOTIFICATIONS 항목 및 `notifications`·`notification_settings`·`device_tokens` 데이터 계약을 함께 만족한다.

## 확정된 동작

1. 앱 내부 알림 목록과 읽지 않은 개수를 조회할 수 있다.
2. 사용자는 개별 알림을 읽음 처리하거나 전체를 읽음 처리할 수 있다.
3. 푸시 알림 설정은 다음 7개 항목으로 축소한다.
   - 새 게시글
   - 내 게시글 반응: 댓글, 좋아요
   - 일정 변경 알림: 등록, 수정, 삭제
   - 일정 시작 알림: 전날 09:00과 시간 일정의 시작 1시간 전 알림에 함께 적용
   - 건당 리포트
   - 일일 리포트
   - 그룹 요청 알림: 초대 요청, 가입 요청
4. 사용자는 자신의 알림 설정을 조회·수정할 수 있다.
5. 사용자는 기기 푸시 토큰을 등록하고 해제할 수 있다.
6. 내부 알림은 `notifications`에 저장되며, 푸시 설정이 꺼져 있어도 내부 알림 저장 자체를 생략하지 않는다.
7. 푸시 발송은 해당 설정이 켜져 있고 사용자의 활성 기기 토큰이 있는 경우에만 시도한다.
8. 내부 알림은 게시글·댓글·좋아요·일정·리포트·그룹 요청 등 관련 대상과 연결될 수 있다.
9. 초대 코드로 생성된 가입 요청 알림은 해당 그룹의 현재 활성 관리자 전원에게만 전달한다.
10. 알림의 `title`과 `body`는 스냅샷으로 보관하여 관련 게시글·일정이 삭제되어도 알림 문구를 유지한다.
11. 푸시 성공·실패 전송 이력은 현재 저장하지 않는다.
12. 7개 푸시 알림 설정의 최초 기본값은 모두 `true`다.
13. 같은 기기 토큰 문자열은 시스템 전체에서 한 행만 가지며, 활성 토큰은
    동시에 한 사용자만 소유한다. 등록은 동시 요청에서도 중복 행이 생기지
    않는 원자적 upsert로 처리한다.
14. 같은 사용자의 재등록은 기존 행의 ID를 유지해 활성화하고, 다른 사용자의
    등록은 계정 전환으로 보아 같은 행의 소유권을 새 사용자에게 이전한다.
    정확한 opaque token을 제출한 인증 사용자를 현재 기기의 token
    보유자로 본다.
15. 신규 등록은 `201`, 재등록·재활성화·소유권 이전은 `200`이며 모두
    `기기 토큰 등록 성공`과 활성화된 같은 응답 데이터를 사용한다.
16. 정상 로그아웃과 인증 상태에서 감지한 OS 알림 권한 철회는 현재 기기의
    토큰만 비활성화하고 다른 기기는 유지한다. 회원 탈퇴는 모든 기기 토큰을
    탈퇴 트랜잭션에서 비활성화한다.
17. 토큰 해제는 행을 삭제하지 않는 소프트 비활성화이며, 본인 토큰이 없거나
    이미 비활성이어도 성공한다.
18. 도메인 이벤트별 내부 알림 수신자와 자기 활동 제외 규칙은 다음과 같다.

    | 알림 유형·사건 | 수신자 | 자기 활동 제외 |
    |---|---|---|
    | `GROUP_JOIN_REQUEST` 가입 요청 생성 | 해당 그룹의 현재 활성 관리자 전원 | 해당 없음 |
    | `GROUP_JOIN_REQUEST` 승인·거절 | 해당 가입 요청의 신청자 | 해당 없음 |
    | `NEW_POST` 게시글 생성 | 해당 그룹의 현재 활성 구성원 전원 | 작성자 제외 |
    | `POST_ACTIVITY` 댓글·반응 생성 | 해당 게시글 작성자 | 작성자 본인의 댓글·반응 제외 |
    | `EVENT_CHANGED` 일정 생성 | 지정 참여자, 참여자가 없으면 현재 활성 그룹 구성원 전원 | 생성자 제외 |
    | `EVENT_CHANGED` 일정 수정 | 수정 전·후 지정 참여자의 합집합, 둘 다 없으면 현재 활성 그룹 구성원 전원 | 수정자 제외 |
    | `EVENT_CHANGED` 일정 삭제 | 삭제 직전 지정 참여자, 참여자가 없으면 현재 활성 그룹 구성원 전원 | 삭제자 제외 |
    | `EVENT_REMINDER` 일정 시작 | 지정 참여자, 참여자가 없으면 현재 활성 그룹 구성원 전원 | 제외하지 않음 |
    | `CALL_REPORT` 건별 리포트 생성 | 해당 피보호자와 같은 그룹의 현재 활성 보호자 전원 | 해당 없음 |
    | `DAILY_REPORT` 일일 리포트 생성 | 해당 피보호자와 같은 그룹의 현재 활성 보호자 전원 | 해당 없음 |

    게시글이 여러 그룹에 각각 생성되면 그룹별 `NEW_POST` 사건으로 처리한다.
    댓글은 생성할 때만, 반응은 새 반응 행이 만들어질 때만 알림을 생성하며
    수정·삭제·반응 해제에는 새 알림을 만들지 않는다.
19. 일정 시작 외 새 내부 알림은
    `<도메인>:<원본 ID>:<행위>[:<변경 UUID>]` 형식의
    `source_event_key`를 사용한다. 가입 요청·게시글·댓글·반응·리포트 생성과
    가입 요청 결정은 원본 ID와 행위로 키를 고정한다. 일정 생성은 일정 ID와
    `CREATED`, 일정 수정·삭제는 일정 ID·행위와 이벤트 생성 때 한 번 만든
    UUID를 사용한다. 같은 이벤트를 다시 처리하면 처음 정한 키를 재사용한다.
20. 같은 수신자와 `source_event_key`가 이미 있으면 기존 알림을 성공 결과로
    보고 새 행이나 두 번째 푸시를 만들지 않는다. `EVENT_REMINDER`는 기존
    수신자·일정·유형·알림 시점 종류 부분 Unique만 사용한다.
21. 도메인 서비스는 원 업무 트랜잭션 안에서 이벤트를 발행하고 내부 알림도
    커밋 전에 같은 트랜잭션으로 저장한다. 원 업무가 롤백되면 알림도 남지
    않는다. 외부 푸시는 원 업무와 내부 알림이 커밋된 뒤 새 알림에만
    시도하며, 실패해도 원 업무나 내부 알림을 롤백하지 않는다.
22. 알림의 `title`·`body`는 수신자별 스냅샷이며 다음 문구를 사용한다.

    | 사건 | `title` | `body` |
    |---|---|---|
    | 가입 요청 생성 | `새 가입 요청이 있어요` | `{신청자 이름}님이 {그룹명} 그룹 가입을 요청했어요.` |
    | 가입 승인 | `가입 요청이 승인됐어요` | `{그룹명} 그룹에 가입됐어요.` |
    | 가입 거절 | `가입 요청이 거절됐어요` | `{그룹명} 그룹 가입 요청이 거절됐어요.` |
    | 게시글 생성 | `새 게시글이 올라왔어요` | `{작성자 표시 이름}님이 새 게시글을 올렸어요.` |
    | 댓글 생성 | `게시글에 새 댓글이 달렸어요` | `{행위자 표시 이름}님이 회원님의 게시글에 댓글을 남겼어요.` |
    | 반응 생성 | `게시글에 새 반응이 생겼어요` | `{행위자 표시 이름}님이 회원님의 게시글에 반응했어요.` |
    | 일정 생성 | `새 일정이 등록됐어요` | `"{일정 제목}" 일정이 등록됐어요.` |
    | 일정 수정 | `일정이 변경됐어요` | `"{일정 제목}" 일정이 변경됐어요.` |
    | 일정 삭제 | `일정이 삭제됐어요` | `"{삭제 직전 일정 제목}" 일정이 삭제됐어요.` |
    | 전날 일정 알림 | `내일 일정이 있어요` | `"{일정 제목}" 일정이 내일 시작돼요.` |
    | 1시간 전 일정 알림 | `곧 일정이 시작돼요` | `"{일정 제목}" 일정이 1시간 후 시작돼요.` |
    | 건별 리포트 생성 | `통화 리포트가 준비됐어요` | `{피보호자 표시 이름}님의 통화 리포트를 확인해 보세요.` |
    | 일일 리포트 생성 | `오늘의 리포트가 준비됐어요` | `{피보호자 표시 이름}님의 오늘 리포트를 확인해 보세요.` |

    수신자별 개인 호칭이 있으면 해당 수신자용 스냅샷에만 적용한다. 필요한
    이름이나 제목이 비정상적으로 없으면 임의 대체 문구를 만들지 않고 사건을
    실패로 기록하며 내부 알림을 만들지 않는다.
23. 운영 푸시는 Firebase Admin SDK를 구현한 `PushSender` 포트로 전송한다.
    비밀키는 저장소에 넣지 않고 `GOOGLE_APPLICATION_CREDENTIALS`로
    주입한다. 로컬·테스트는 비활성 또는 가짜 어댑터를 사용할 수 있지만,
    운영에서 푸시가 활성화됐는데 자격 증명이 없으면 서버 시작을 실패시킨다.
24. 알림 설정 행이 없으면 기본값 `true`로 본다. 설정이 활성화된 수신자의
    모든 활성 token에 기기 우선순위 없이 전송한다. 표시 payload는 저장된
    `title`·`body`, data payload는 `notificationId`·`type`만 포함한다.
    Firebase가 token을 `UNREGISTERED` 또는 명백한 무효 token으로 응답하면
    그 token만 soft deactivate한다. 다른 일시적 실패는 구조화 로그만 남기고
    자동 재시도하거나 전송 이력을 저장하지 않는다.
25. 일정 알림 작업은 1분마다 현재 시각까지 최근 1시간의 예정 시점을
    조회한다. 일정이 예정 시점 전에 존재했다면 서버 중단·재시작으로 놓친
    최근 1시간의 알림을 복구하고, 반복 조회 중복은 기존 Unique로 막는다.
    일정 등록·시간 변경 시 이미 지난 예정 시점은 즉시 보내지 않으며 한
    시간보다 오래 지난 알림도 보내지 않는다. 같은 일정·수신자·
    `reminder_slot`은 시작 시각이 바뀌어도 다시 만들지 않는다.

확정된 예외:

- 조건: 사용자가 해당 푸시 설정을 비활성화했다.
  - 처리: 내부 알림은 보존하되 해당 유형의 푸시 발송은 하지 않는다.
- 조건: 활성 기기 토큰이 없다.
  - 처리: 내부 알림은 보존하고 푸시 발송은 수행하지 않는다.
- 조건: 동일 기기 토큰을 다시 등록한다.
  - 처리: 기존 ID를 유지하고 현재 인증 사용자에게 소유권을 맞춘 뒤 활성
    상태와 기기 유형·수정 시각을 갱신한다.
- 조건: 다른 사용자가 소유한 토큰을 해제하려 한다.
  - 처리: 토큰 상태를 바꾸지 않고 `403 FORBIDDEN`을 반환한다.

## 구현 규칙

- 권한: 사용자는 자신의 알림 목록·읽음 상태·설정·기기 토큰만 관리한다. 이벤트를 만든 주체와 수신자는 알림 발생 도메인의 권한 규칙을 따른다.
- 상태와 전이: 내부 알림은 생성 후 읽지 않음에서 읽음으로 전이한다. 기기 토큰은 활성·비활성 상태를 관리한다.
- API:
  - 처리 주체: 알림 저장·읽음 상태·설정·기기 토큰은 Spring Boot가 처리한다. 통화·리포트·게시글 이벤트를 만드는 각 도메인은 알림 이벤트를 발생시킬 수 있다.
  - Method와 Path: `API-NOTIFICATIONS-001~008`을 [API 계약](../contracts/API.md)에서 참조한다.
  - 핵심 입력·결과: 기기 토큰 등록·해제, 읽지 않은 개수·목록 조회, 개별·전체 읽음 처리, 7개 설정 조회·수정은 API 계약에 정의된 형식을 사용한다.
  - MVP의 `deviceType`은 정확히 `ANDROID`만 허용한다. `token`은 공백이 아닌
    최대 500자의 opaque 문자열이며 정규화하거나 형식을 추측하지 않는다.
  - 로그인 성공 또는 인증 세션 복원 후 OS 알림 권한과 토큰이 있으면
    등록한다. 인증 상태에서 FCM 토큰이 갱신되면 다시 등록하고, 인증 전
    토큰은 로컬에 보관했다가 인증 후 등록한다. 권한이 거부된 상태에서는
    등록하지 않는다.
  - 일반 로그아웃은 인증이 유효한 동안 현재 token으로
    `API-NOTIFICATIONS-008`을 먼저 호출한 뒤 인증 로그아웃을 요청한다.
    OS 알림 권한 철회도 현재 또는 직전에 발급받아 보관 중인 token을
    인증 상태에서 비활성화한다.
  - 계정 전환은 기존 계정으로 현재 토큰을 해제한 뒤 로그아웃하고, 새 계정
    로그인 후 같은 토큰을 다시 등록하는 순서다.
- 이벤트:
  - 각 도메인 변경과 내부 알림은 같은 트랜잭션에서 처리하고, 푸시는 커밋
    후에만 시도한다.
  - 비일정 알림의 멱등 키와 일정 시작 알림의 부분 Unique는
    [DATA_MODEL](../contracts/DATA_MODEL.md)을 따른다.
  - 푸시 payload에는 화면 경로나 리포트 상세 같은 민감한 내용을 넣지 않는다.
- 데이터:
  - 관련 엔티티: `notifications`, `notification_settings`, `device_tokens`.
  - 읽기·쓰기 소유자: Spring Boot가 알림 API와 관련 데이터의 모든 읽기·쓰기를 처리한다.
  - 주요 제약조건: 알림 수신자·관련 대상 FK, 설정 유형별 사용자 unique,
    토큰의 전역 unique·단일 활성 소유권·활성 상태는
    [DATA_MODEL](../contracts/DATA_MODEL.md)을 따른다.
- 화면:
  - 진입점: 앱 내부 알림 목록, 알림 설정 화면, 기기 권한·토큰 등록 흐름.
  - 사용자에게 표시할 결과: 읽지 않은 개수, 알림 내용·읽음 상태, 기본값이 켜진 7개 설정 토글을 표시한다.
  - 모바일 화면은 React Native로 구현한다.

## 인수 조건

### AC-001

- Given: 수신자에게 새 게시글 이벤트가 발생한다.
- When: 알림 이벤트를 처리한다.
- Then: 내부 알림이 저장되고, 새 게시글 설정이 활성화되어 활성 기기 토큰이 있으면 푸시를 시도한다.

### AC-002

- Given: 사용자가 특정 알림을 읽지 않은 상태로 보유한다.
- When: 개별 읽음 처리를 요청한다.
- Then: 해당 알림만 읽음 상태로 바뀌고 읽지 않은 개수가 갱신된다.

### AC-003

- Given: 사용자가 7개 푸시 설정 중 하나를 변경한다.
- When: 설정을 저장한다.
- Then: 해당 설정 유형만 사용자의 설정으로 갱신된다.

### AC-004

- Given: 사용자의 특정 푸시 설정이 꺼져 있다.
- When: 해당 이벤트가 발생한다.
- Then: 내부 알림은 저장되지만 해당 유형의 푸시는 보내지 않는다.

### AC-005

- Given: 같은 토큰이 기존 사용자 또는 다른 사용자에게 이미 등록되어 있다.
- When: 인증 사용자가 같은 토큰을 다시 등록한다.
- Then: 중복 행 없이 같은 ID를 현재 사용자 소유의 활성 상태로 갱신하고
  `200`을 반환한다.

### AC-006

- Given: 사용자가 로그인·세션 복원 또는 FCM 토큰 갱신을 완료했고 OS 알림
  권한이 허용되어 있다.
- When: 앱이 토큰 등록 흐름을 실행한다.
- Then: 인증 사용자로 토큰을 등록하며, 권한이 거부된 상태에서는 등록
  요청을 보내지 않는다.

### AC-007

- Given: 본인 토큰이 없거나 이미 비활성이다.
- When: 토큰 해제를 요청한다.
- Then: 행을 삭제하지 않고 `204 No Content`를 반환하며 다른 기기 토큰은
  유지한다.

### AC-008

- Given: 사용자가 여러 기기에 활성 토큰을 보유하고 있다.
- When: 회원 탈퇴가 처리된다.
- Then: 탈퇴 트랜잭션에서 해당 사용자의 모든 기기 토큰이 비활성화된다.

### AC-009

- Given: 동일한 가입 요청·게시글·댓글·반응·일정 변경·리포트 사건을 두 번
  처리한다.
- When: 내부 알림을 저장하고 푸시 조건을 평가한다.
- Then: 수신자별 내부 알림과 푸시 시도는 한 번뿐이다.

### AC-010

- Given: 원 도메인 업무가 롤백되거나, 커밋 뒤 외부 푸시가 실패한다.
- When: 알림 처리 결과를 확인한다.
- Then: 롤백된 업무에는 내부 알림과 푸시가 없고, 푸시 실패는 커밋된 원
  업무와 내부 알림을 되돌리지 않는다.

### AC-011

- Given: 일정 알림 예정 시점에 서버가 중단됐다가 한 시간 안에 다시
  시작했거나, 새 일정의 알림 예정 시점이 이미 지났다.
- When: 1분 주기 일정 알림 작업이 실행된다.
- Then: 기존 일정의 최근 1시간 누락만 중복 없이 복구하고 새 일정의 이미
  지난 알림은 즉시 보내지 않는다.

## 미결정 사항

- 설정 화면의 저장 시점과 실패 표시.
- 내부 알림의 보존 기간·삭제 정책.
- 로그아웃 전 token 비활성화 요청이 실패했을 때 로그아웃 지속·재시도
  방식과, 인증되지 않은 상태에서 OS 알림 권한 철회를 감지했을 때의 서버
  비활성화 방식.
