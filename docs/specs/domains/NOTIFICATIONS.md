# [NOTIFICATIONS] 앱·푸시 알림

> 상태: 일부 확정
> 기준: 2026-07-28, 최신 Notion API·ERD·Spring Boot 단일 백엔드 결정

## AI 작업 컨텍스트

- 목적: 서비스의 내부 알림을 제공하고, 사용자가 푸시 알림 종류별 수신 여부와 기기 토큰을 관리할 수 있게 한다.
- 포함 범위: 앱 내부 알림 목록·읽음 처리, 푸시 설정 7개, 기기 토큰 등록·해제, 알림 발생 대상.
- 제외 범위: 전송 재시도·플랫폼별 메시지 형식은 확정하지 않는다.
- 핵심 규칙: 내부 알림 저장과 푸시 전달은 분리한다. 내부 알림은 이벤트 대상자에게 생성하고, 푸시는 해당 설정이 활성화되어 있으며 활성 기기 토큰이 있을 때만 보낸다.
- 완료 조건: 알림 동작은 이 문서와 [API 계약](../contracts/API.md)의 NOTIFICATIONS 항목 및 `notifications`·`notification_settings`·`device_tokens` 데이터 계약을 함께 만족한다.

## 확정된 동작

1. 앱 내부 알림 목록과 읽지 않은 개수를 조회할 수 있다.
2. 사용자는 개별 알림을 읽음 처리하거나 전체를 읽음 처리할 수 있다.
3. 푸시 알림 설정은 다음 7개 항목으로 축소한다.
   - 새 게시글
   - 내 게시글 반응: 댓글, 좋아요
   - 일정 변경 알림: 등록, 수정, 삭제
   - 일정 시작 알림: 전날 09:00과 시간 일정의 시작 1시간 전 알림에 함께 적용
   - 건당 리포트
   - 일일 리포트
   - 그룹 요청 알림: 초대 요청, 가입 요청
4. 사용자는 자신의 알림 설정을 조회·수정할 수 있다.
5. 사용자는 기기 푸시 토큰을 등록하고 해제할 수 있다.
6. 내부 알림은 `notifications`에 저장되며, 푸시 설정이 꺼져 있어도 내부 알림 저장 자체를 생략하지 않는다.
7. 푸시 발송은 해당 설정이 켜져 있고 사용자의 활성 기기 토큰이 있는 경우에만 시도한다.
8. 내부 알림은 게시글·댓글·좋아요·일정·리포트·그룹 요청 등 관련 대상과 연결될 수 있다.
9. 초대 코드로 생성된 가입 요청 알림은 해당 그룹 관리자에게만 전달한다.
10. 알림의 `title`과 `body`는 스냅샷으로 보관하여 관련 게시글·일정이 삭제되어도 알림 문구를 유지한다.
11. 푸시 성공·실패 전송 이력은 현재 저장하지 않는다.
12. 7개 푸시 알림 설정의 최초 기본값은 모두 `true`다.
13. 같은 기기 토큰 문자열은 시스템 전체에서 한 행만 가지며, 활성 토큰은
    동시에 한 사용자만 소유한다. 등록은 동시 요청에서도 중복 행이 생기지
    않는 원자적 upsert로 처리한다.
14. 같은 사용자의 재등록은 기존 행의 ID를 유지해 활성화하고, 다른 사용자의
    등록은 계정 전환으로 보아 같은 행의 소유권을 새 사용자에게 이전한다.
    정확한 opaque token을 제출한 인증 사용자를 현재 기기의 token
    보유자로 본다.
15. 신규 등록은 `201`, 재등록·재활성화·소유권 이전은 `200`이며 모두
    `기기 토큰 등록 성공`과 활성화된 같은 응답 데이터를 사용한다.
16. 정상 로그아웃과 인증 상태에서 감지한 OS 알림 권한 철회는 현재 기기의
    토큰만 비활성화하고 다른 기기는 유지한다. 회원 탈퇴는 모든 기기 토큰을
    탈퇴 트랜잭션에서 비활성화한다.
17. 토큰 해제는 행을 삭제하지 않는 소프트 비활성화이며, 본인 토큰이 없거나
    이미 비활성이어도 성공한다.

확정된 예외:

- 조건: 사용자가 해당 푸시 설정을 비활성화했다.
  - 처리: 내부 알림은 보존하되 해당 유형의 푸시 발송은 하지 않는다.
- 조건: 활성 기기 토큰이 없다.
  - 처리: 내부 알림은 보존하고 푸시 발송은 수행하지 않는다.
- 조건: 동일 기기 토큰을 다시 등록한다.
  - 처리: 기존 ID를 유지하고 현재 인증 사용자에게 소유권을 맞춘 뒤 활성
    상태와 기기 유형·수정 시각을 갱신한다.
- 조건: 다른 사용자가 소유한 토큰을 해제하려 한다.
  - 처리: 토큰 상태를 바꾸지 않고 `403 FORBIDDEN`을 반환한다.

## 구현 규칙

- 권한: 사용자는 자신의 알림 목록·읽음 상태·설정·기기 토큰만 관리한다. 이벤트를 만든 주체와 수신자는 알림 발생 도메인의 권한 규칙을 따른다.
- 상태와 전이: 내부 알림은 생성 후 읽지 않음에서 읽음으로 전이한다. 기기 토큰은 활성·비활성 상태를 관리한다.
- API:
  - 처리 주체: 알림 저장·읽음 상태·설정·기기 토큰은 Spring Boot가 처리한다. 통화·리포트·게시글 이벤트를 만드는 각 도메인은 알림 이벤트를 발생시킬 수 있다.
  - Method와 Path: `API-NOTIFICATIONS-001~008`을 [API 계약](../contracts/API.md)에서 참조한다.
  - 핵심 입력·결과: 기기 토큰 등록·해제, 읽지 않은 개수·목록 조회, 개별·전체 읽음 처리, 7개 설정 조회·수정은 API 계약에 정의된 형식을 사용한다.
  - MVP의 `deviceType`은 정확히 `ANDROID`만 허용한다. `token`은 공백이 아닌
    최대 500자의 opaque 문자열이며 정규화하거나 형식을 추측하지 않는다.
  - 로그인 성공 또는 인증 세션 복원 후 OS 알림 권한과 토큰이 있으면
    등록한다. 인증 상태에서 FCM 토큰이 갱신되면 다시 등록하고, 인증 전
    토큰은 로컬에 보관했다가 인증 후 등록한다. 권한이 거부된 상태에서는
    등록하지 않는다.
  - 일반 로그아웃은 인증이 유효한 동안 현재 token으로
    `API-NOTIFICATIONS-008`을 먼저 호출한 뒤 인증 로그아웃을 요청한다.
    OS 알림 권한 철회도 현재 또는 직전에 발급받아 보관 중인 token을
    인증 상태에서 비활성화한다.
  - 계정 전환은 기존 계정으로 현재 토큰을 해제한 뒤 로그아웃하고, 새 계정
    로그인 후 같은 토큰을 다시 등록하는 순서다.
- 데이터:
  - 관련 엔티티: `notifications`, `notification_settings`, `device_tokens`.
  - 읽기·쓰기 소유자: Spring Boot가 알림 API와 관련 데이터의 모든 읽기·쓰기를 처리한다.
  - 주요 제약조건: 알림 수신자·관련 대상 FK, 설정 유형별 사용자 unique,
    토큰의 전역 unique·단일 활성 소유권·활성 상태는
    [DATA_MODEL](../contracts/DATA_MODEL.md)을 따른다.
- 화면:
  - 진입점: 앱 내부 알림 목록, 알림 설정 화면, 기기 권한·토큰 등록 흐름.
  - 사용자에게 표시할 결과: 읽지 않은 개수, 알림 내용·읽음 상태, 기본값이 켜진 7개 설정 토글을 표시한다.
  - 모바일 화면은 React Native로 구현한다.

## 인수 조건

### AC-001

- Given: 수신자에게 새 게시글 이벤트가 발생한다.
- When: 알림 이벤트를 처리한다.
- Then: 내부 알림이 저장되고, 새 게시글 설정이 활성화되어 활성 기기 토큰이 있으면 푸시를 시도한다.

### AC-002

- Given: 사용자가 특정 알림을 읽지 않은 상태로 보유한다.
- When: 개별 읽음 처리를 요청한다.
- Then: 해당 알림만 읽음 상태로 바뀌고 읽지 않은 개수가 갱신된다.

### AC-003

- Given: 사용자가 7개 푸시 설정 중 하나를 변경한다.
- When: 설정을 저장한다.
- Then: 해당 설정 유형만 사용자의 설정으로 갱신된다.

### AC-004

- Given: 사용자의 특정 푸시 설정이 꺼져 있다.
- When: 해당 이벤트가 발생한다.
- Then: 내부 알림은 저장되지만 해당 유형의 푸시는 보내지 않는다.

### AC-005

- Given: 같은 토큰이 기존 사용자 또는 다른 사용자에게 이미 등록되어 있다.
- When: 인증 사용자가 같은 토큰을 다시 등록한다.
- Then: 중복 행 없이 같은 ID를 현재 사용자 소유의 활성 상태로 갱신하고
  `200`을 반환한다.

### AC-006

- Given: 사용자가 로그인·세션 복원 또는 FCM 토큰 갱신을 완료했고 OS 알림
  권한이 허용되어 있다.
- When: 앱이 토큰 등록 흐름을 실행한다.
- Then: 인증 사용자로 토큰을 등록하며, 권한이 거부된 상태에서는 등록
  요청을 보내지 않는다.

### AC-007

- Given: 본인 토큰이 없거나 이미 비활성이다.
- When: 토큰 해제를 요청한다.
- Then: 행을 삭제하지 않고 `204 No Content`를 반환하며 다른 기기 토큰은
  유지한다.

### AC-008

- Given: 사용자가 여러 기기에 활성 토큰을 보유하고 있다.
- When: 회원 탈퇴가 처리된다.
- Then: 탈퇴 트랜잭션에서 해당 사용자의 모든 기기 토큰이 비활성화된다.

## 미결정 사항

- 설정 화면의 저장 시점과 실패 표시.
- 내부 알림의 보존 기간·삭제 정책과 일정 시작 외 유형의 중복 방지 정책.
- 푸시 전송 실패 재시도, 발송 결과로 확인한 만료 토큰의 자동 정리,
  다중 기기 발송 우선순위.
- 로그아웃 전 token 비활성화 요청이 실패했을 때 로그아웃 지속·재시도
  방식과, 인증되지 않은 상태에서 OS 알림 권한 철회를 감지했을 때의 서버
  비활성화 방식.
- 일정 시작 알림 Spring Scheduler의 장애·서버 재시작 후 복구 정책. 전송 시각 자체는 [일정 스펙](./CALENDAR.md)의 고정 규칙을 따른다.
