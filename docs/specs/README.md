# 공식 로컬 스펙

`docs/specs/`는 코드와 테스트의 공식 구현 기준입니다. 팀원과 Codex는
일반 구현에서 Notion에 접근하지 않고 이 폴더만으로 동작, 계약, 권한,
예외와 미결정 범위를 이해할 수 있어야 합니다.

Notion의 `2 AI`는 기획과 의사결정의 원본입니다. 최신 확정 결정을 이
폴더로 이관할 때만 원본 대조에 사용하며, 구현 중 Notion을 추가로 읽어야
완성되는 스펙은 만들지 않습니다.

`docs/` 바로 아래의 기존 문서는 이관 근거 또는 참고 자료입니다. 내용이
다를 때는 이 폴더의 공식 스펙과 계약을 구현 기준으로 사용합니다.

## 서비스와 대표 사용자 흐름

이 서비스는 가족의 일상 공유와 AI 전화를 연결해 소통 공백을 보완한다.
AI가 가족을 대체하는 서비스로 표현하거나 구현하지 않는다.

1. 보호자와 피보호자가 초대 코드·관리자 승인을 거쳐 같은 가족 그룹에
   참여한다.
2. 그룹 구성원이 피드에 근황을 공유하고 캘린더에 일정을 등록한다.
3. 안정화된 게시글은 AI 대화용 요약으로 분석된다.
4. 피보호자가 원할 때 AI 전화를 시작하면 현재 그룹의 당일 게시글 맥락,
   관심사와 필요한 Tool 조회 결과가 대화에 사용된다.
5. 통화 후 건별 리포트가 생성되고, 하루의 건별 리포트는
   `Asia/Seoul` 기준 22시에 Spring Scheduler가 일일 리포트로 집계한다.
6. 보호자는 리포트로 근황과 전달 메시지를 확인하고 가족 소통을 이어 간다.

공통 기능은 가족 피드·게시글 보관함, 공유 캘린더, 그룹 관리, 앱 내부
알림·푸시 설정이며, 역할 전용 기능은 피보호자의 AI 전화와 보호자의
리포트·활동·주간 랭킹이다.

## 읽는 순서

1. [`INDEX.md`](./INDEX.md)에서 작업 영역을 찾습니다.
2. 관련 도메인 문서의 `AI 작업 컨텍스트`를 먼저 읽습니다.
3. 세부 판단이 필요할 때만 같은 문서의 본문을 읽습니다.
4. 도메인 문서가 직접 가리키는 `COMMON`, `API`, `DATA_MODEL`,
   `UI_AND_NAVIGATION`만 추가로 읽습니다.
5. 전체 이관 누락이나 매핑 상태를 조사할 때만
   [`COVERAGE.md`](./COVERAGE.md)를 읽습니다.

## 폴더 구조

```text
specs/
├─ README.md
├─ INDEX.md                   # 일반 구현용 가벼운 라우터
├─ COVERAGE.md                # 원본 전체의 이관 누락 검증
├─ COMMON.md                  # 여러 도메인이 공유하는 확정 규칙
├─ UI_AND_NAVIGATION.md       # 역할별 이동과 공통 화면 상태
├─ TEMPLATE.md
├─ domains/                   # 사용자 기능 도메인 8개
└─ contracts/
   ├─ API.md                  # Notion 활성 API 명세의 로컬 계약
   └─ DATA_MODEL.md           # 최신 확정 ERD의 로컬 계약
```

## 상태와 작성 원칙

- `확정`은 구현과 테스트의 기준으로 사용할 수 있습니다.
- `일부 확정`은 `확정된 동작`만 구현 기준이며 `미결정 사항`은 기준이 아닙니다.
- 미결정, 미고려, 검토 중인 내용을 확정 규칙이나 인수 조건으로 바꾸지 않습니다.
- 확인되지 않은 오류 코드, 메시지, 제한값, 재시도 정책을 만들지 않습니다.
- 도메인 문서는 프론트엔드와 백엔드로 쪼개지 않고 하나의 사용자 기능을
  기준으로 작성합니다.
- 상세 API와 데이터 구조는 도메인 문서에 복제하지 않고 로컬 계약을
  참조합니다.
- 스펙 라우팅이 달라졌을 때만 `INDEX.md`를 수정합니다.
- 이관 범위나 원본 매핑이 달라졌으면 `COVERAGE.md`를 함께 확인합니다.

## 변경 제안과 승인 반영

- 스펙과 구현의 차이를 발견하면 `$spec-change-recorder`로
  `../spec-changes/pending/`에 제안만 기록합니다.
- 변경 제안은 승인 전까지 공식 스펙도, 구현 기준도 아닙니다.
- 사용자가 특정 제안과 승인 범위를 명시한 경우에만
  `$spec-change-applier`로 공식 스펙을 반영합니다.
- 반영 시 관련 도메인, 계약, UI, `COVERAGE.md`를 확인하고, 라우팅이
  달라졌을 때만 `INDEX.md`를 수정합니다.
- 검증이 끝난 완결 제안만 `../spec-changes/applied/`로 이동합니다.
- 이번 최초 이관처럼 최신 확정 원본을 그대로 옮기는 작업은 변경 제안으로
  만들지 않습니다.
