# Git 컨벤션

## 목적

Git 기록과 코드 리뷰 흐름을 통일하고, Jira 이슈와 GitLab 작업을 쉽게 추적합니다.

## 기본 작업 흐름

1. Jira 이슈를 확인하거나 생성합니다.
2. 해당 이슈에서 작업 브랜치를 만듭니다.
3. 작은 단위로 커밋합니다.
4. GitLab Merge Request를 생성해 리뷰받습니다.
5. 병합 후 Jira 이슈를 완료 처리합니다.

## 브랜치 이름

형식:

`<type>/<JIRA_KEY>-<짧은-작업명>`

| 작업 유형 | 사용 예시 |
| --- | --- |
| 기능 개발 | `feature/S15P11B104-123-login` |
| 버그 수정 | `fix/S15P11B104-124-token-expire` |
| 리팩터링 | `refactor/S15P11B104-125-auth` |
| 문서 수정 | `docs/S15P11B104-126-git-guide` |
| 설정·기타 | `chore/S15P11B104-127-ci` |

- 브랜치명에는 Jira 이슈 키를 반드시 포함합니다.
- `main`에 직접 커밋하지 않습니다.
- 작업명은 짧고 영문 소문자와 하이픈을 사용합니다.
- Jira 제목의 `[FE]`, `[BE]`, `[AI]`, `[COMMON]` 영역 접두사는 브랜치명에 그대로 복사하지 않습니다. 영역보다 실제 작업 내용을 영문 작업명으로 표현합니다.

## 커밋 메시지

형식:

`[JIRA_KEY] <type>: <작업 내용>`

예시:

```text
[S15P11B104-123] feat: 로그인 폼 구현
[S15P11B104-124] fix: 토큰 만료 처리
[S15P11B104-126] docs: Git 컨벤션 추가
```

커밋 유형:

- `feat`: 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변경 없는 구조 개선
- `docs`: 문서 수정
- `test`: 테스트 추가·수정
- `chore`: 설정, 빌드, 의존성 등 기타 작업
- 하나의 커밋에는 하나의 논리적인 변경만 담습니다.
- `update`, `수정`, `작업`처럼 의미가 모호한 메시지는 사용하지 않습니다.
- 비밀번호, API 키, `.env` 파일 등 민감정보를 커밋하지 않습니다.

## Merge Request

MR 제목 형식:

`[JIRA_KEY] 작업 내용`

예시:

`[S15P11B104-123] 로그인 기능 구현`

Jira 티켓에 영역 접두사가 있으면 MR 작업 내용에는 이를 유지합니다.

```text
Jira: [FE] 통화 리포트 조회 화면 구현
MR: [S15P11B104-123] [FE] 통화 리포트 조회 화면 구현
```

커밋 메시지는 기존 `[JIRA_KEY] <type>: <작업 내용>` 형식을 유지하며, Jira 영역 접두사를 커밋 타입 앞에 추가하지 않습니다.

MR 본문에 다음 내용을 작성합니다.

- 작업 목적
- 주요 변경 사항
- 테스트 방법과 결과
- 리뷰어가 확인할 내용
- 관련 Jira 이슈 키

규칙:

- 하나의 MR은 하나의 Jira 이슈를 기준으로 작성합니다.
- 작업 중이면 Draft MR로 올립니다.
- CI가 통과하고 리뷰가 완료된 뒤 병합합니다.
- 병합 후 작업 브랜치를 삭제합니다.
- 관련 없는 기능이나 대규모 리팩터링을 하나의 MR에 섞지 않습니다.

## Jira 연동 규칙

브랜치, 커밋, MR에 Jira 이슈 키를 정확히 작성합니다.

```text
Jira 이슈 생성
→ feature/S15P11B104-123-login
→ [S15P11B104-123] feat: 로그인 폼 구현
→ [S15P11B104-123] 로그인 기능 구현 MR
→ 병합 후 Jira 완료 처리
```

영역 접두사가 있는 티켓도 브랜치와 커밋 형식은 동일하고, MR 제목의 작업 내용에만 Jira 제목의 접두사를 유지합니다.

이슈 키가 누락되거나 오타가 나면 GitLab과 Jira 연결이 생성되지 않을 수 있습니다.

## 금지 사항

- `main` 직접 커밋
- 검증되지 않은 코드를 강제 푸시
- 공유 브랜치에 `push --force`
- 민감정보 커밋
- 서로 관련 없는 작업을 한 커밋·MR에 혼합
- Jira 이슈 키 없이 작업 진행

## 브랜치 전략

팀 작업은 `main`, `develop`, 작업 브랜치로 구분합니다.

```text
feature/*, fix/*
        ↓ Merge Request
     develop
        ↓ 배포 전 Merge Request
       main
```

- `main`: 배포 가능한 안정 버전만 유지합니다.
- `develop`: 팀원 작업을 통합하고 테스트하는 브랜치입니다.
- `feature/*`, `fix/*`: `develop`에서 생성해 작업합니다.
- 작업 브랜치는 `develop`을 대상으로 Merge Request를 생성합니다.
- 배포할 때 `develop`에서 `main`으로 Merge Request를 생성합니다.
- `main`과 `develop`에는 직접 push하지 않습니다.
- CI 통과와 코드 리뷰 완료 후 병합합니다.
- 병합이 끝난 작업 브랜치는 삭제합니다.
