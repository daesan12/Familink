# Jira Convention

## 목적과 적용 범위

이 문서는 S15P11B104 프로젝트에서 Jira 티켓을 생성하고, 담당하고, GitLab 작업과 연결해 완료하는 기준입니다.

- 적용 시점: 2026-07-27 이후 생성하거나 수정하는 Jira 티켓
- Jira 프로젝트: `S15P11B104`
- Git 규칙: `docs/team-rules/git-convention.md`
- 이 문서와 Jira의 실제 필드·워크플로가 충돌하면 생성 가능한 필드와 전이 값은 Jira의 현재 설정을 따르되, 아래 팀 필수 규칙은 생략하지 않습니다.

## 핵심 규칙

### 1. Story Points는 필수입니다

- 모든 작업 단위에는 Story Points를 입력합니다.
- 허용 값은 `1`, `2`, `3`, `5`, `8`입니다.
- Story Points는 개인의 작업 시간이 아니라 티켓의 상대적인 복잡도, 작업량, 불확실성을 함께 나타냅니다.
- `8`을 초과한다고 판단되는 작업은 하나의 큰 티켓으로 만들지 않고, 독립적으로 완료 여부를 확인할 수 있는 여러 티켓으로 나눕니다.
- 값이 없거나 허용 범위를 벗어난 티켓은 작업을 시작하지 않습니다.

### 2. 신규 하위 작업은 사용하지 않습니다

- 2026-07-27 이후에는 새로운 `하위 작업`을 생성하지 않습니다.
- 작업을 나눌 때는 `작업`, `스토리`, `버그` 중 목적에 맞는 일반 티켓을 각각 생성합니다.
- 분리된 티켓은 같은 Epic에 포함하거나 Jira의 `Blocks` 또는 `Relates` 링크로 관계를 표시합니다.
- 기존에 생성된 하위 작업은 삭제하거나 일반 티켓으로 강제 변환하지 않고, 현재 담당자와 범위를 유지한 채 완료합니다.
- 기존 하위 작업을 완료하는 과정에서도 새로운 하위 작업을 추가하지 않습니다.

### 3. 티켓당 담당자는 한 명입니다

- 하나의 Jira 티켓에는 한 명의 담당자만 지정합니다.
- 여러 사람이 함께 일해야 하면 각자의 독립적인 완료 결과를 기준으로 일반 티켓을 나눕니다.
- 협업자와 리뷰어는 설명, 댓글, 이슈 링크 또는 GitLab Merge Request에 기록하며 Jira 담당자 필드를 공유하지 않습니다.
- 담당 범위를 분리할 수 없는 공동 작업은 한 명을 최종 책임자(DRI)로 지정하고, 나머지 참여자는 설명에 역할을 기록합니다.

## 이슈 유형

| 유형 | 사용 기준 |
| --- | --- |
| `에픽` | 여러 일반 티켓을 묶는 큰 목표 |
| `스토리` | 사용자 관점의 가치와 완료 조건이 명확한 작업 |
| `작업` | 기본 개발, 조사, 문서, 설정 작업 |
| `버그` | 기존 동작이 기대와 다르게 작동하는 문제 |
| `하위 작업` | 신규 생성 금지. 기존 티켓 완료에만 사용 |

유형이 명시되지 않았다면 `작업`을 기본으로 사용합니다. 실제 결함은 `버그`, 명시적인 사용자 스토리는 `스토리`, 큰 목표는 `에픽`으로 분류합니다.

## 제목과 영역 접두사

신규 하위 작업을 사용하지 않으므로, 하나의 사용자 가치를 여러 기술 영역의 일반 티켓으로 나눌 때는 제목 접두사로 실행 영역을 구분합니다.

- `스토리`는 사용자가 얻는 가치와 전체 완료 조건을 표현합니다. 기술 영역별 담당자를 구분하기 위해 같은 스토리를 `[FE]`, `[BE]`, `[AI]` 버전으로 복제하지 않습니다.
- FE·BE·AI 각각이 독립적인 사용자 가치와 관찰 가능한 완료 조건을 제공하는 별도 스토리라면 영역 접두사를 사용할 수 있습니다. 단순히 담당 영역만 다른 동일 스토리에는 이 예외를 적용하지 않습니다.
- `[COMMON]`은 여러 영역이 공유하는 기술 기반 `작업` 전용이며 `스토리`에는 사용하지 않습니다.
- 스토리를 실현하기 위해 분리한 `작업`에는 영역 접두사를 붙입니다.
  - `[FE]`: Android·웹 등 사용자 클라이언트 작업
  - `[BE]`: 서버·API·데이터 처리 작업
  - `[AI]`: AI 모델·프롬프트·AI 파이프라인 작업
  - `[COMMON]`: 두 영역 이상이 공동으로 사용하는 기반 작업
- 영역 분할과 무관한 기획, 조사, 발표, 단일 범위 작업에는 접두사를 붙이지 않습니다.
- 다른 영역 접두사가 필요하면 임의로 만들지 않고 팀 합의 후 이 문서에 추가합니다.
- 접두사는 Jira 제목의 분류 정보입니다. Jira 키나 Git 커밋 타입을 제목에 붙이지 않습니다.

예시:

```text
스토리: 보호자는 통화 리포트를 조회할 수 있다
작업: [FE] 통화 리포트 조회 화면 구현
작업: [BE] 통화 리포트 조회 API 구현
작업: [AI] 통화 요약 생성 결과 연동
```

영역별 티켓은 각각 독립적인 완료 기준과 담당자 한 명을 가져야 합니다. 같은 목표라면 동일 Epic에 포함하고 원본 스토리와 `Relates`로 연결하며, 선후 관계가 있으면 `Blocks`로 표현합니다. 원본 스토리에는 전체 사용자 가치의 완료 여부를 판단할 DRI 한 명을 지정합니다.

## 필수 필드

새 일반 티켓에는 다음 정보를 모두 기록합니다.

- 요약: 위 규칙에 따른 선택적 영역 접두사와 구체적인 한국어 작업명. Jira 키나 Git 커밋 타입은 제외
- 설명: 목적, 작업 내용, 관찰 가능한 완료 기준
- 담당자: 한 명
- 기한: 실제 달력 날짜
- Story Points: `1`, `2`, `3`, `5`, `8` 중 하나
- 우선순위: 별도 합의가 없으면 Jira 기본값 사용

```markdown
[목적]

<이 작업이 필요한 이유>

[작업 내용]

* <수행할 핵심 작업>

[완료 기준]

* <완료 여부를 확인할 수 있는 결과>
```

모르는 요구사항, 구현 방식, 수치, 일정은 임의로 만들어 넣지 않습니다.

## 작업 분할

하나의 티켓이 `8` Story Points를 넘거나 담당자가 여러 명이어야 한다면 다음 순서로 나눕니다.

1. 각 결과를 독립적으로 완료하고 검증할 수 있는지 확인합니다.
2. 공동 사용자 가치는 하나의 `스토리`, 기술 영역별 실행 결과는 일반 `작업`으로 생성합니다.
3. 각 티켓에 담당자 한 명과 Story Points를 지정합니다.
4. 영역별 `작업` 제목에 `[FE]`, `[BE]`, `[AI]`, `[COMMON]` 중 해당 접두사를 붙입니다.
5. 같은 목표라면 동일 Epic에 포함합니다.
6. 원본 스토리와는 `Relates`, 선후 관계가 있으면 `Blocks`로 연결합니다.

업무를 나눌 수 없다는 이유만으로 동일한 내용의 티켓을 사람 수만큼 복제하지 않습니다.

## 상태와 GitLab 연동

기본 흐름은 다음과 같습니다.

```text
Jira 티켓 생성
→ 담당자·기한·Story Points 확인
→ 작업 브랜치 생성 및 Jira 진행 중 전환
→ 커밋과 푸시
→ GitLab Merge Request 생성 및 Jira에 URL 연결
→ 리뷰·CI 완료 후 병합
→ 병합 결과 확인 후 Jira 완료 전환
```

- 하나의 작업 브랜치와 Merge Request는 하나의 Jira 티켓을 기준으로 합니다.
- 브랜치, 커밋, MR 제목에는 `docs/team-rules/git-convention.md` 형식에 맞는 Jira 키를 포함합니다.
- MR이 병합되기 전에는 Jira 티켓을 완료 처리하지 않습니다.
- Jira 티켓을 완료하기 전에 MR의 병합 상태와 대상 브랜치가 맞는지 확인합니다.
- 기존 하위 작업도 동일한 검증 절차로 마무리할 수 있습니다.

## 완료 점검

티켓을 완료하려면 다음 조건을 확인합니다.

- 담당자가 한 명으로 지정되어 있습니다.
- Story Points가 허용 값으로 입력되어 있습니다.
- 완료 기준을 실제 결과로 확인했습니다.
- 관련 MR이 대상 브랜치에 병합되었습니다.
- Jira에 MR URL이 연결되어 있습니다.

신규 하위 작업 생성, 담당자 없는 티켓, Story Points 없는 티켓, 여러 담당자를 전제로 한 단일 티켓은 허용하지 않습니다.
