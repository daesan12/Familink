# 도메인 이벤트 알림 수신자·중복 방지·푸시 전달 계약 확정

- 상태: 승인·반영 완료
- 제안자: Codex
- 작성일: 2026-07-31
- 차단 변경: 예
- 영향 스펙·계약: `docs/specs/domains/NOTIFICATIONS.md`,
  `docs/specs/domains/GROUPS_AND_MEMBERSHIP.md`,
  `docs/specs/domains/FEED_AND_MEDIA.md`,
  `docs/specs/domains/CALENDAR.md`,
  `docs/specs/domains/REPORTS.md`,
  `docs/specs/contracts/DATA_MODEL.md`
- 관련 작업: `S15P11B104-125` 및 가입 요청·피드·일정·리포트 생성 작업

## 기존 내용

공식 스펙은 다음 공통 원칙을 확정한다.

- 앱 내부 알림은 푸시 설정과 관계없이 `notifications`에 저장한다.
- 푸시는 해당 유형의 설정이 활성화되어 있고 수신자의 활성 기기 token이
  있을 때만 시도한다.
- 가입 요청 생성 알림은 해당 그룹 관리자에게만 전달한다.
- 일정 시작 알림은 참여자가 있으면 현재 활성 참여자, 없으면 현재 활성 그룹
  구성원 전부에게 전달한다.
- 일정 시작 알림은
  `(receiver_user_id, related_event_id, type, reminder_slot)` 조합으로
  중복을 방지한다.
- `title`과 `body`는 관련 대상이 삭제돼도 남는 스냅샷이다.
- 푸시 성공·실패 전송 이력은 저장하지 않는다.

그러나 `S15P11B104-125`의 완료 기준인 “대상 이벤트에 앱 내부 알림이 중복
없이 생성되고 조건을 만족할 때만 푸시가 시도된다”를 구현하려면 다음 계약이
추가로 필요하다.

- 일정 시작 외 이벤트의 정확한 수신자와 자기 활동 알림 제외 여부
- 동일한 도메인 이벤트가 다시 처리될 때 사용할 멱등 키
- 원 업무 트랜잭션, 내부 알림 저장, 외부 푸시 호출 사이의 경계
- 유형과 사건별 `title`·`body`
- 푸시 payload, 여러 기기 전송, 실패와 만료 token 처리
- 서버 재시작 및 이미 지난 일정 알림 시점 처리

현재 백엔드에는 `Notification`, `NotificationSetting`, `DeviceToken` 엔티티와
일정 시작 알림용 부분 Unique만 있다. 알림 저장소·서비스·도메인 이벤트
리스너·Firebase 전송 어댑터는 아직 없다.

## 제안 내용

### E1. 이벤트별 수신자

수신자는 사건이 발생한 그룹의 현재 활성 구성원을 기준으로 계산한다.

| 알림 유형·사건 | 수신자 | 자기 활동 제외 |
|---|---|---|
| `GROUP_JOIN_REQUEST` 가입 요청 생성 | 해당 그룹의 현재 활성 관리자 전원 | 해당 없음 |
| `GROUP_JOIN_REQUEST` 승인·거절 | 해당 가입 요청의 신청자 | 해당 없음 |
| `NEW_POST` 게시글 생성 | 해당 그룹의 현재 활성 구성원 전원 | 작성자 제외 |
| `POST_ACTIVITY` 댓글·반응 생성 | 해당 게시글 작성자 | 작성자 본인의 댓글·반응은 제외 |
| `EVENT_CHANGED` 일정 생성 | 지정 참여자, 참여자가 없으면 현재 활성 그룹 구성원 전원 | 생성자 제외 |
| `EVENT_CHANGED` 일정 수정 | 수정 전·후 지정 참여자의 합집합, 둘 다 없으면 현재 활성 그룹 구성원 전원 | 수정자 제외 |
| `EVENT_CHANGED` 일정 삭제 | 삭제 직전 지정 참여자, 참여자가 없으면 현재 활성 그룹 구성원 전원 | 삭제자 제외 |
| `EVENT_REMINDER` 일정 시작 | 기존 확정 규칙 그대로 사용 | 제외하지 않음 |
| `CALL_REPORT` 건별 리포트 생성 | 해당 피보호자와 같은 그룹의 현재 활성 보호자 전원 | 해당 없음 |
| `DAILY_REPORT` 일일 리포트 생성 | 해당 피보호자와 같은 그룹의 현재 활성 보호자 전원 | 해당 없음 |

- 게시글 한 번 쓰기로 여러 그룹에 각각 게시글 행이 만들어지면 그룹별
  `NEW_POST` 사건으로 처리한다.
- 댓글은 생성할 때만, 반응은 새 반응 행이 만들어질 때만
  `POST_ACTIVITY`를 만든다. 수정·삭제·반응 해제에는 새 알림을 만들지 않는다.
- 일정 수정으로 참여 대상에서 빠진 구성원도 변경 사실을 알 수 있도록
  수정 전·후 참여자의 합집합을 사용한다.
- 수신자별 개인 호칭이 있으면 해당 수신자에게 저장하는 `title`·`body`에만
  그 호칭을 적용한다.

### E2. 비일정 알림의 중복 방지

- `notifications`에 nullable `source_event_key VARCHAR(160)`을 추가한다.
- `source_event_key IS NOT NULL`인 행에는
  `(receiver_user_id, source_event_key)` 부분 Unique를 둔다.
- 새 비일정 알림은 처리 한 번마다 생성한 임의 키가 아니라 아래처럼 원본
  사건을 다시 처리해도 같은 안정적인 키를 사용한다.
  - 가입 요청: 요청 ID와 `CREATED`·`APPROVED`·`REJECTED`
  - 게시글: 게시글 ID와 `CREATED`
  - 댓글·반응: 댓글 ID 또는 반응 행 ID와 `CREATED`
  - 일정 생성: 일정 ID와 `CREATED`
  - 일정 수정·삭제: 일정 ID, `UPDATED`·`DELETED`, 해당 변경 이벤트가
    만들어질 때 한 번 생성해 이벤트 객체가 계속 보존하는 UUID
  - 리포트: 건별 또는 일일 리포트 ID와 `CREATED`
- 문자열 형식은
  `<도메인>:<원본 ID>:<행위>[:<변경 UUID>]`로 고정한다. 하나의 도메인
  이벤트를 여러 수신자에게 처리하거나 같은 리스너가 다시 처리할 때는
  처음 정한 문자열을 그대로 재사용한다.
- 같은 수신자와 `source_event_key`가 이미 존재하면 기존 알림을 성공 결과로
  보고 새 행과 두 번째 푸시를 만들지 않는다.
- `EVENT_REMINDER`는 기존
  `(receiver_user_id, related_event_id, type, reminder_slot)` 부분
  Unique를 계속 사용하며 `source_event_key`로 이중 관리하지 않는다.

### E3. 저장 트랜잭션과 푸시 시점

- 도메인 서비스는 가입 요청·게시글·댓글·반응·일정·리포트 변경을 저장하는
  트랜잭션 안에서 도메인 이벤트를 발행한다.
- 앱 내부 알림 행은 원 업무가 커밋되기 전에 같은 트랜잭션에서 저장한다.
  원 업무가 롤백되면 내부 알림도 남지 않는다.
- 외부 푸시는 원 업무와 내부 알림이 모두 커밋된 뒤 새로 저장된 알림에
  대해서만 시도한다.
- 푸시 실패는 이미 커밋된 원 업무나 앱 내부 알림을 롤백하지 않는다.
- 이 티켓에서는 범용 outbox, 전송 이력 테이블, 메시지 브로커를 추가하지
  않는다.

### E4. `title`·`body` 스냅샷

알림 생성 시 아래 문구를 수신자별 스냅샷으로 저장한다.

| 사건 | `title` | `body` |
|---|---|---|
| 가입 요청 생성 | `새 가입 요청이 있어요` | `{신청자 이름}님이 {그룹명} 그룹 가입을 요청했어요.` |
| 가입 승인 | `가입 요청이 승인됐어요` | `{그룹명} 그룹에 가입됐어요.` |
| 가입 거절 | `가입 요청이 거절됐어요` | `{그룹명} 그룹 가입 요청이 거절됐어요.` |
| 게시글 생성 | `새 게시글이 올라왔어요` | `{작성자 표시 이름}님이 새 게시글을 올렸어요.` |
| 댓글 생성 | `게시글에 새 댓글이 달렸어요` | `{행위자 표시 이름}님이 회원님의 게시글에 댓글을 남겼어요.` |
| 반응 생성 | `게시글에 새 반응이 생겼어요` | `{행위자 표시 이름}님이 회원님의 게시글에 반응했어요.` |
| 일정 생성 | `새 일정이 등록됐어요` | `"{일정 제목}" 일정이 등록됐어요.` |
| 일정 수정 | `일정이 변경됐어요` | `"{일정 제목}" 일정이 변경됐어요.` |
| 일정 삭제 | `일정이 삭제됐어요` | `"{삭제 직전 일정 제목}" 일정이 삭제됐어요.` |
| 전날 일정 알림 | `내일 일정이 있어요` | `"{일정 제목}" 일정이 내일 시작돼요.` |
| 1시간 전 일정 알림 | `곧 일정이 시작돼요` | `"{일정 제목}" 일정이 1시간 후 시작돼요.` |
| 건별 리포트 생성 | `통화 리포트가 준비됐어요` | `{피보호자 표시 이름}님의 통화 리포트를 확인해 보세요.` |
| 일일 리포트 생성 | `오늘의 리포트가 준비됐어요` | `{피보호자 표시 이름}님의 오늘 리포트를 확인해 보세요.` |

- 관련 이름이나 제목이 비정상적으로 없으면 빈 문자열을 조합하지 않고
  `새 알림이 도착했어요` 같은 별도 문구를 추측하지도 않는다. 해당 사건을
  실패로 기록하고 내부 알림을 만들지 않아 데이터 결함을 드러낸다.
- 화면 문구나 레이아웃은 이 제안과 작업 범위에 포함하지 않는다.

### E5. 푸시 payload와 실패 처리

- Spring Boot에는 `PushSender` 포트를 두고 운영 어댑터는 Firebase Admin
  SDK를 사용한다.
- 비밀키는 저장소에 넣지 않고 표준
  `GOOGLE_APPLICATION_CREDENTIALS`로 주입한다.
- 로컬·테스트에서는 비활성 또는 가짜 어댑터를 사용할 수 있다. 운영에서
  푸시가 활성화됐는데 자격 증명이 없으면 서버 시작을 실패시켜 조용한 누락을
  막는다.
- 알림 설정 행이 아직 없으면 확정된 기본값 `true`로 본다. `false`면 앱
  내부 알림만 남기고 푸시를 건너뛴다.
- 조건을 만족하면 수신자의 활성 token 전부에 전송하고 기기 우선순위를
  두지 않는다.
- 표시 payload에는 저장된 `title`·`body`, data payload에는
  `notificationId`와 `type`만 담는다. 화면 경로 또는 민감한 리포트 내용을
  payload에 넣지 않는다.
- Firebase가 token을 `UNREGISTERED` 또는 명백한 무효 token으로 응답하면
  그 token만 soft deactivate한다.
- 그 밖의 일시적 실패는 구조화 로그만 남기고 자동 재시도하지 않는다.
  전송 성공·실패 이력도 저장하지 않는다.

### E6. 일정 알림 재시작 복구와 지난 시점

- 일정 알림 작업은 1분마다 실행하고, 현재 시각까지 최근 1시간 안에 예정돼
  있던 알림을 함께 조회한다.
- 일정이 해당 예정 시점 전에 이미 존재했다면 서버 중단·재시작으로 놓친
  최근 1시간의 알림을 생성한다. 기존 Unique로 반복 조회 중복을 막는다.
- 일정을 등록하거나 시간을 변경한 시점에 알림 예정 시각이 이미 지났다면
  그 시점의 알림은 즉시 보내지 않고 생략한다.
- 한 시간보다 오래 지난 알림은 늦게 보내지 않는다.
- 시간 일정의 전날 알림이 이미 생성된 뒤 시작 시각이 바뀌어도 같은
  `reminder_slot` 알림을 다시 만들지 않는다. 새 시작 시각의 1시간 전
  알림은 아직 생성되지 않았다면 기존 규칙으로 한 번 생성할 수 있다.

검증 문장:

1. 같은 가입 요청·게시글·댓글·반응·일정 변경·리포트 사건을 두 번 처리해도
   수신자별 내부 알림과 푸시 시도는 한 번뿐이다.
2. 자기 게시글·댓글·반응 또는 자기 일정 변경으로 자신에게 새 활동 알림이
   생기지 않는다.
3. 푸시 설정이 꺼져 있거나 활성 token이 없으면 내부 알림만 저장된다.
4. 원 업무가 롤백되면 내부 알림과 푸시가 모두 발생하지 않고, 푸시 실패는
   원 업무와 내부 알림을 되돌리지 않는다.
5. 서버 재시작 후 최근 1시간 안에 놓친 일정 알림만 복구되고, 새 일정의
   이미 지난 알림은 즉시 발송되지 않는다.
6. 화면이나 레이아웃을 새로 구현하지 않고 서버 알림 생성·전달만 변경된다.

## 변경 근거

- 수신자를 추측해 구현하면 다른 그룹 정보나 리포트 접근 권한이 없는
  사용자에게 알림을 보낼 수 있다.
- 애플리케이션 이벤트는 같은 처리가 다시 실행될 수 있으므로 DB Unique가
  없는 메모리 검사만으로는 동시 실행 중복을 막을 수 없다.
- 외부 푸시를 원 업무 트랜잭션 안에서 호출하면 네트워크 실패가 게시글·일정
  저장까지 실패시키거나, 롤백된 업무의 푸시가 먼저 발송될 수 있다.
- `notificationId`와 `type`만 전달하면 잠금 화면 payload에 리포트나 가족
  활동 상세를 노출하지 않으면서 앱이 서버의 최신 권한 상태를 다시 확인할
  수 있다.
- 기존 앱 내부 알림, 설정, token 구조를 재사용하고 범용 메시지 인프라를
  추가하지 않는 것이 현재 MVP 범위에서 가장 단순하다.

## 확인된 영향

- 영향 도메인: 가입 요청, 피드, 일정, 통화·일일 리포트, 앱 내부·푸시 알림
- 영향 계약: `notifications.source_event_key`와 부분 Unique, 사건별 수신자,
  문구 스냅샷, 푸시 payload·실패 처리, 일정 알림 복구
- 영향 화면: 없음. 기존 알림 화면과 진입 동작은 구현 범위에서 제외
- 검증 범위: 수신자·자기 제외, 트랜잭션 롤백, 동시 중복 사건, 설정
  on/off, token 없음·여러 개·무효 token, Firebase 실패, 일정 작업 반복·재시작
