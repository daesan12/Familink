# 로그인 ID 허용 문자 규칙 확정

- 상태: 승인·반영 완료
- 제안자: 이경호
- 작성일: 2026-07-28
- 차단 변경: 아니오
- 영향 스펙·계약: `contracts/DATA_MODEL.md` `users` 활성 계정 제약, `contracts/API.md` `API-AUTH-001`·`API-AUTH-002`·`API-USERS-002`
- 관련 작업: S15P11B104-114
- 관련 제안: [`CHG-S15P11B104-114-common-response-envelope.md`](../pending/CHG-S15P11B104-114-common-response-envelope.md), [`CHG-S15P11B104-114-auth-token-storage-and-ttl.md`](../pending/CHG-S15P11B104-114-auth-token-storage-and-ttl.md)

## 기존 내용

`docs/specs/contracts/DATA_MODEL.md` 「`users`」 절은 로그인 ID의 길이만 규정한다.

> 활성 계정 제약: 아이디 5~15자, 이름 2~10자이며 필수 회원정보는 NULL일 수 없다.

`docs/specs/domains/ACCOUNT_AND_PROFILE.md` 「확정된 동작」 1번도 회원가입 입력 항목에 로그인 ID가 포함된다는 사실만 적는다. 즉 로그인 ID에 어떤 문자를 허용하는지는 어느 문서에도 정의되어 있지 않다.

## 제안 내용

로그인 ID의 허용 문자 집합을 확정한다. 다음 중 하나를 선택해 `contracts/DATA_MODEL.md` 「`users`」 절의 활성 계정 제약에 추가한다.

- 안 1: 영문 소문자·숫자만 허용한다.
- 안 2: 영문 대소문자·숫자·밑줄(`_`)만 허용한다.
- 안 3: 공백 문자만 금지하고 나머지는 허용한다.

검증 문장: 결정된 문자 집합을 벗어난 로그인 ID로 `API-AUTH-002` 회원가입을 요청하면 `400 INVALID_REQUEST`를 받고, `API-AUTH-001` 중복 확인도 같은 조건으로 `400 INVALID_REQUEST`를 받는다.

## 변경 근거

- `S15P11B104-114` 구현에서 로그인 ID 검증을 길이 조건만으로 두면 `" testuser"`처럼 앞뒤 공백을 포함한 값이 유효한 로그인 ID가 된다. `login_id` UNIQUE 제약과 중복 확인 조회는 문자를 그대로 비교하므로, `API-AUTH-001`이 `testuser`를 사용 가능하다고 응답한 뒤 육안으로 구별되지 않는 별도 계정이 만들어질 수 있다.
- 우선 조치로 `backend`의 회원가입 요청과 중복 확인 파라미터에 공백 문자를 금지하는 검증(`@Pattern(regexp = "\\S+")`)을 동일하게 적용했다. 이는 스펙에 명시된 규칙이 아니라 계정 식별 오류를 막기 위한 최소 조치다.
- 이 조치는 ASCII 공백만 배제한다. 줄바꿈 없는 공백(U+00A0)이나 표의문자 공백(U+3000)은 통과하므로 육안으로 구별되지 않는 로그인 ID가 만들어질 여지가 완전히 닫히지 않는다. 문자 집합을 확정하지 않고는 이 문제를 끝까지 막을 수 없다.
- 프론트엔드도 회원가입 화면에서 같은 규칙으로 입력을 검증해야 하므로 양쪽이 같은 기준을 공유해야 한다.

## 확인된 영향

- 영향 도메인: 계정·프로필의 회원가입, 로그인 ID 중복 확인, 프로필 수정 시 로그인 ID 변경
- 영향 계약: `contracts/DATA_MODEL.md` 「`users`」 절의 활성 계정 제약에 허용 문자 규칙을 추가한다. `API-AUTH-001`·`API-AUTH-002`·`API-USERS-002`의 `400 INVALID_REQUEST` 판정 조건이 구체화된다. Method, Path, 요청·응답 필드 구성은 변경하지 않는다.
- 영향 화면: 확인 필요. 회원가입과 프로필 수정 화면의 로그인 ID 입력 검증 문구와 조건에 영향을 준다.
- 검증 범위: 결정된 문자 집합의 경계값에 대한 `API-AUTH-001`·`API-AUTH-002` 통합 테스트. 현재는 공백 포함 로그인 ID 거부만 검증되어 있다.

## 결정 및 반영

- 결정: 전체 승인. 2026-07-29에는 `API-AUTH-001`·`002`의 5~15자와
  `\S+` 공백 금지만 승인했다. 2026-07-30에는 기존 세 안 대신
  ASCII 영문 대·소문자와 숫자(`[A-Za-z0-9]`)를 허용하고 대소문자를
  구분하며 소문자로 정규화하지 않는 규칙을 승인했다. 이 규칙은
  `API-AUTH-001`·`002`·`003`과 `API-USERS-002`에 동일하게 적용한다.
  기존 저장 계정에는 소급 적용하거나 마이그레이션하지 않는다.
- 결정자: 사용자
- 결정일: 2026-07-29, 2026-07-30
- 승인 근거: 사용자가 2026-07-29에는 구현·확정된 부분만 승인했고,
  2026-07-30에는 영문·숫자 허용, 대소문자 구분, 소문자 정규화 안 함을
  명시한 뒤 기존 계정 소급 적용은 하지 않아도 된다고 결정했다.
- 반영 문서: `docs/specs/domains/ACCOUNT_AND_PROFILE.md`,
  `docs/specs/contracts/API.md`, `docs/specs/contracts/DATA_MODEL.md`
