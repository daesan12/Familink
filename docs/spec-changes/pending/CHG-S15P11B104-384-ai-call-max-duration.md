# AI 통화 최대 시간 상한과 시간 만료 종료 안내 규정 추가

- 상태: 제안
- 제안자: 손수호
- 작성일: 2026-08-07
- 차단 변경: 아니오
- 영향 스펙·계약: `docs/specs/domains/AI_CALL.md`
- 관련 작업: S15P11B104-384

## 기존 내용

- `docs/specs/domains/AI_CALL.md`의 "확정된 동작" 1번은 "피보호자는 자동 발신 시간이나
  횟수 제한 없이 원할 때 AI 전화 탭에서 페르소나를 선택하고 (...) 통화를 시작한다"로,
  **발신 시점과 횟수**에만 제한이 없음을 규정한다. 시작된 통화 한 건이 얼마나 길게
  이어질 수 있는지는 규정하지 않는다.
- 같은 문서 "확정된 동작" 6번은 "통화 화면에는 통화 시간, 음소거, 통화 종료, 스피커
  제어와 AI 발화 실시간 자막을 제공한다"로, 통화 시간의 **표시**만 규정한다. 그 값에
  상한이 있는지는 규정하지 않는다.
- 같은 문서 "확정된 동작" 13번은 종료 원인을 `USER_REQUESTED` 또는 `CONNECTION_LOST`
  두 가지로 규정하고, `IN_PROGRESS` 중 `USER_REQUESTED`는 `COMPLETED`,
  `CONNECTION_LOST`는 `INCOMPLETE`가 된다고 규정한다. 시간 경과로 끝나는 통화는
  이 전이표에 없다.
- 같은 문서 "확정된 동작" 16번의 90초 lease는 "살아 있는 Sideband 세션을 소유한 백엔드
  인스턴스가 30초마다 자신의 세션 lease를 갱신한다"로, **백엔드 인스턴스 장애 복구**
  수단이다. 통화 길이를 제한하는 장치가 아니다.
- 같은 문서 "미결정 사항"에도 통화 최대 시간·무응답·자동 종료가 없어, 미결정으로
  추적되는 것조차 아닌 스펙 공백이다.
- `docs/specs/` 전체에 통화 한 건의 최대 지속 시간 규정이 없다.
- 화면 규정에서 종료 결과는 "사용자에게 표시할 결과: (...) 종료 결과"로만 기술되고,
  종료 사유별 안내 문구 구분은 규정하지 않는다.

## 제안 내용

`docs/specs/domains/AI_CALL.md`의 "확정된 동작"에 다음을 추가한다. 항 번호는 반영
시점에 결정한다.

1. 한 통화가 이어질 수 있는 최대 시간은 10분이다. 통화 시간이 10분에 도달하면 단말이
   통화를 스스로 마감한다.
2. 이 마감은 사용자가 통화 종료를 요청한 것과 같은 경로로 처리한다. 종료 원인은
   `USER_REQUESTED`이고 `IN_PROGRESS` 세션은 `COMPLETED`가 되며, 전사 finalization과
   건별 리포트 생성 조건은 사용자 종료와 동일하다. 시간 만료 전용 `termination_type`은
   추가하지 않는다.
3. 상한 도달로 끝난 통화의 종료 결과 화면에는 시간이 다 되어 마무리되었음을 알리는
   안내를 표시한다. 사용자가 직접 종료한 통화와 안내 문구가 구분된다.
4. 상한 도달을 예고하는 사전 경고는 표시하지 않는다.
5. 이 상한은 대화 활성 여부와 무관하게 적용된다. 사용자가 계속 말하고 있어도 10분에
   마감되고, 침묵 중이어도 10분 전에는 마감되지 않는다.

`AC-002`와 별개로 다음 인수 조건을 추가한다. 번호는 반영 시점에 결정한다.

- Given: 통화가 `IN_PROGRESS`이고 통화 시간이 10분에 도달했다.
- When: 단말이 통화를 마감한다.
- Then: 세션이 `USER_REQUESTED`로 접수되어 `COMPLETED`가 되고, 전사 무결성과 건별
  리포트 생성 조건이 사용자 종료와 동일하게 적용되며, 종료 결과 화면에 시간 만료
  안내가 표시된다.

## 변경 근거

- 현재 통화는 스스로 끝나지 않는다. 코드에서 확인한 사실은 다음과 같다.
  - `backend/src/main/java/com/ssafy/s15p11b104/domain/call/service/OpenAiRealtimeGateway.java`의
    `createSessionJson`이 `turn_detection`에 `server_vad`, `threshold`,
    `interrupt_response`만 지정한다. `server_vad`는 사용자 음성이 감지될 때만 응답
    생성을 트리거하므로 침묵은 아무 이벤트도 만들지 않는다. 침묵 후 모델 응답을
    자동으로 트리거하는 OpenAI의 `idle_timeout_ms`는 설정되어 있지 않다.
  - 음소거는 `frontend/android/app/src/main/java/com/s15p11b104app/aicall/AiCallWebRtc.kt`에서
    `audioTrack.setEnabled(false)`만 수행하므로 OpenAI 입장에서는 무음과 같은 입력이다.
    별도 종료 경로가 없다.
  - `backend/src/main/java/com/ssafy/s15p11b104/domain/call/service/CallSessionLeaseService.java`의
    lease 갱신은 Sideband 소켓 생존만 확인하므로, 무응답 통화일수록 세션이 오히려
    안정적으로 유지된다.
  - `frontend/android/app/src/main/java/com/s15p11b104app/aicall/AiCallContent.kt`의 통화
    시간 카운터는 1초마다 증가만 하고 상한이 없었다.
  - `docs/qa/two-user-emulator-qa.md`의 P5-09가 무음 통화 종료를 실측했고, 사용자가
    직접 종료해야만 끝나는 것으로 기록되어 있다.
- 상한이 필요한 이유는 비용이다. 화면을 켜 둔 채 방치된 통화가 OpenAI Realtime 비용을
  무한히 누적할 수 있다. 10분은 대화가 만족스러울 만큼 길면서 비용이 예측 가능한
  수준이라고 판단해 팀이 정했다.
- 새 `termination_type`을 만들지 않는 근거는 얻는 것이 없기 때문이다. 리포트 생성
  여부와 세션 상태 전이가 `USER_REQUESTED`와 완전히 같은데, 새 값을 만들면
  `docs/specs/contracts/API.md`의 `API-CALLS-003` enum, 백엔드
  `CallTerminationType`, DB 제약, 이 문서의 상태 전이표까지 연쇄로 바뀐다.
- 4번을 규정하는 근거는 범위 통제다. 사전 경고는 통화 화면에 새 상태와 표시를 추가해야
  하므로 이번 범위에서 제외했다. 대신 3번으로 종료 후 안내를 제공해, 통화가 갑자기
  끊긴 것을 피보호자가 고장으로 오해하지 않게 한다.
- 5번을 명시하는 근거는 이 상한이 "무응답 자동 종료"로 오해되기 쉽기 때문이다. 이
  제안은 침묵을 감지하지 않는다. S15P11B104-384의 원래 조사 대상이던 무응답 처리와
  다른 문제를 다룬다는 점을 스펙에 남긴다.

## 확인된 영향

- 영향 도메인: `AI_CALL`. 다른 도메인 규칙은 바뀌지 않는다.
- 영향 계약: 없다고 판단한다. `docs/specs/contracts/API.md`의
  `API-CALLS-001`~`API-CALLS-003`은 기존 `termination_type` 값만 사용하므로 요청·응답
  스키마가 바뀌지 않는다. `docs/specs/contracts/DATA_MODEL.md`의 `call_sessions`,
  `call_transcripts`, `call_reports` 스키마와 제약도 바뀌지 않는다. 서버는 시간 만료
  종료와 사용자 종료를 구분하지 않는다.
- 영향 화면: IA `F-2` 통화 중 화면(상한 도달 시 자동으로 종료 단계로 전환)과 종료 결과
  화면(안내 문구 분기). 통화 중 화면의 표시 요소는 추가되지 않는다.
- 검증 범위: `:app:testDebugUnitTest`의 `com.s15p11b104app.aicall.*`와
  `:app:assembleDebug`. 상한 판정과 종료 안내 문구는 순수 함수 단위 테스트로 고정했다.
  에뮬레이터에서는 상한 상수를 임시로 낮춰 (1) 상한 도달 시 종료 화면 전환,
  (2) 시간 만료 안내 문구 표시, (3) 서버 세션이 `COMPLETED`로 마감되고 건별 리포트가
  생성됨, (4) 상한 전 사용자 종료는 기존 문구 유지를 수동 확인한다. 실제 통화 경로는
  계기 테스트로 검증할 수 없어 수동 확인이 필요하다.
- 커버리지 갱신 후보: `docs/specs/COVERAGE.md`의 `REQ-011 AI 통화 제어` 행. 확인 필요.
- 관련 제안: `CHG-S15P11B104-370-ai-call-barge-in-suppression.md`(AI 발화 중 마이크
  게이팅), `CHG-S15P11B104-310-call-control-default-state.md`(통화 제어 기본 상태).
  세 제안 모두 `AC-002` 주변을 건드리므로 반영 시 항 번호가 겹치지 않게 조정한다.

## 확인이 필요한 질문

- 상한이 단말에만 있어도 되는지 확인 필요. 앱 프로세스가 멈춘 채 WebRTC 연결만 살아
  있으면 단말 타이머가 돌지 않아 상한이 걸리지 않고, lease는 소켓 생존만 보므로
  세션이 유지된다. 이 잔여 위험을 허용할지, 백엔드 측 하드 캡을 별도 티켓으로 만들지
  결정이 필요하다.
- 10분이 적정한지 확인 필요. 실사용 통화 길이 데이터가 아직 없어 팀 판단으로 정한
  값이다. 시연·QA 결과에 따라 조정될 수 있다.
- 무음이 지속될 때 AI가 먼저 말을 거는 `idle_timeout_ms` 도입 여부는 이번 제안 범위
  밖이다. S15P11B104-384 조사에서 미구현으로 확인했으며, 별도 결정이 필요하다.
