# 공통 응답 봉투를 로컬 API 계약에 기록

- 상태: 일부 승인
- 제안자: 이경호
- 작성일: 2026-07-28
- 차단 변경: 예
- 영향 스펙·계약: `contracts/API.md` 공통 경계, 활성 API 59건 전체의 성공·오류 응답 본문
- 관련 작업: S15P11B104-114

## 기존 내용

`docs/specs/contracts/API.md` 서두(6~13행)는 성공 결과 표기의 성격만 규정하고 실제 응답 본문 형태를 정의하지 않는다.

> 표의 성공 결과는 원본 성공 응답의 핵심 `data` 내용이다. 공통 응답 봉투의 세부 형태가 행에 적혀 있지 않다면 임의로 만들지 않는다.

`docs/specs/COMMON.md`에도 응답 형식 규정이 없다. 따라서 로컬 스펙만으로는 응답 본문을 구현할 수 없다.

한편 팀 Notion의 「API 명세서 2차 수정본」에는 봉투 형식이 각 API 페이지의 응답 예시로 이미 확정되어 있다. 즉 이 항목은 팀에서 결정되지 않은 사항이 아니라, 결정된 내용이 로컬 스펙에 옮겨지지 않은 누락이다.

## 제안 내용

`AGENTS.md`의 「Notion 또는 외부 문서를 읽어야만 이해되는 스펙을 만들지 않는다」 원칙에 따라, Notion에 확정된 다음 봉투 형식을 `contracts/API.md` 「공통 경계」에 기록한다.

성공 응답 본문은 최상위에 `success`, `message`, `data`를 가진다.

```json
{
  "success": true,
  "message": "로그인 아이디 중복 확인 성공",
  "data": { "available": true }
}
```

- `success`는 `true`다.
- `message`는 API별 성공 문구다. 확인된 문구는 `API-AUTH-001` 「로그인 아이디 중복 확인 성공」, `API-AUTH-002` 「회원가입 성공」, `API-AUTH-003` 「로그인 성공」이다.
- `data`는 표의 「성공 결과」 열에 적힌 필드로 구성한 객체다.

실패 응답 본문은 최상위에 `success`, `code`, `message`, `errors`를 가지며 `data`를 포함하지 않는다.

```json
{
  "success": false,
  "code": "LOGIN_ID_DUPLICATED",
  "message": "이미 사용 중인 로그인 아이디",
  "errors": []
}
```

- `code`는 표의 「명시 오류」 열에 적힌 오류 코드 문자열이다.
- `message`는 해당 오류의 문구다. 확인된 문구는 `INVALID_REQUEST` 「요청 형식 또는 검증 실패」, `LOGIN_ID_DUPLICATED` 「이미 사용 중인 로그인 아이디」, `INVALID_CREDENTIALS` 「아이디 또는 비밀번호가 일치하지 않습니다.」다.
- `errors`는 검증에 실패한 필드 목록이다. Notion 예시는 빈 배열만 보여 원소 구조가 확정되어 있지 않다. 2026-07-28 사용자 결정에 따라 `{"field": "<필드명>", "message": "<실패 이유>"}` 형태로 구현했다. 이 원소 구조는 팀 확인이 필요하다.
- 본문 없는 성공 응답(`204 No Content`)은 봉투를 포함하지 않는다. `API-AUTH-005`는 Notion에도 「응답 본문 없음」으로 적혀 있다.

검증 문장: 임의의 활성 API를 호출했을 때 성공·실패 응답 본문의 최상위 키 집합이 위 정의와 정확히 일치한다.

## 변경 근거

- `S15P11B104-114`의 4개 인증 API를 구현하려면 응답 본문을 직렬화해야 하므로 봉투 형식 없이는 구현을 완료할 수 없다.
- 로컬 스펙에 형식이 없어 처음에는 `{success, data, error}`로 잘못 구현했고, 2026-07-28 사용자가 Notion 명세를 알려준 뒤 `{success, message, data}`·`{success, code, message, errors}`로 바로잡았다. 로컬 스펙에 기록되어 있었다면 이 왕복이 필요하지 않았다.
- 확인 경로: Notion 「API 명세서 2차 수정본」의 `API-AUTH-001`, `API-AUTH-002`, `API-AUTH-003`, `API-AUTH-005` 각 페이지 응답·Error Response 절.

## 확인된 영향

- 영향 도메인: 계정·프로필(구현 완료), 이후 전체 도메인의 모든 API 응답
- 영향 계약: `contracts/API.md` 「공통 경계」에 봉투 정의를 추가한다. 활성 API 59건의 Method, Path, 상태 코드, 성공 결과 필드 구성은 변경하지 않는다.
- 영향 화면: 없음. 이미 확정된 형식을 기록하는 것이므로 프론트엔드 구현 기준은 달라지지 않는다.
- 검증 범위: 인증 API 4건의 성공·오류 응답 본문을 통합 테스트와 실제 서버 호출로 확인했다. 나머지 API는 각 구현 시점에 동일 형식 적용 여부를 확인해야 한다.

## 확인이 필요한 질문

- 나머지 55건의 성공 `message` 문구를 어디에서 관리할지. API별 고정
  문구라면 각 API 명세에 함께 기록되어야 한다.

## 결정 및 반영

- 결정: 일부 승인. 성공 `{success,message,data}`와 실패
  `{success,code,message,errors}` 봉투, `errors` 원소의 `{field,message}`,
  `204 No Content`의 본문 없음, 구현·확인된 `API-AUTH-001~004` 성공 문구와
  인증 오류 문구를 승인한다. 나머지 API의 성공 `message` 목록은 미확정이므로
  승인 범위에서 제외하고 보류한다.
