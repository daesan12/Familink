# 공통 응답 봉투 형식 확정

- 상태: 제안
- 제안자: 이경호
- 작성일: 2026-07-28
- 차단 변경: 예
- 영향 스펙·계약: `contracts/API.md` 공통 경계, 활성 API 59건 전체의 성공·오류 응답 본문
- 관련 작업: S15P11B104-114

## 기존 내용

`docs/specs/contracts/API.md` 서두(6~13행)는 성공 결과 표기의 성격만 규정하고 실제 응답 본문 형태를 정의하지 않는다.

> 표의 성공 결과는 원본 성공 응답의 핵심 `data` 내용이다. 공통 응답 봉투의 세부 형태가 행에 적혀 있지 않다면 임의로 만들지 않는다.

또한 같은 문서는 오류에 대해 다음을 규정한다.

> 오류가 "명시 없음"인 행에도 구현자가 관례적인 오류 코드를 추가해서는 안 되며, 먼저 계약을 확정해야 한다.

즉 `data`라는 이름의 래핑이 존재한다는 사실만 암시되어 있고, 최상위 키 구성, 성공·실패 판별 방식, 오류 본문의 필드 이름과 타입은 어디에도 정의되어 있지 않다. `docs/specs/COMMON.md`에도 응답 형식 규정이 없다.

## 제안 내용

활성 API 59건 전체가 공유하는 공통 응답 봉투를 다음으로 확정한다.

- 성공 응답 본문은 최상위에 `success`, `data`, `error` 세 키만 가진다.
  - `success`는 `true`다.
  - `data`는 `contracts/API.md` 표의 "성공 결과" 열에 적힌 필드로 구성한 객체다.
  - `error`는 `null`이다.
- 오류 응답 본문은 같은 세 키를 사용한다.
  - `success`는 `false`다.
  - `data`는 `null`이다.
  - `error`는 `code`와 `message` 두 필드를 가진 객체다. `code`는 `contracts/API.md` 표의 "명시 오류" 열에 적힌 오류 코드 문자열(예: `LOGIN_ID_DUPLICATED`)이며, `message`는 사람이 읽을 수 있는 한국어 설명이다.
- 본문 없는 성공 응답(`204 No Content`)은 봉투를 포함하지 않는다.
- HTTP 상태 코드는 `contracts/API.md` 표의 값을 그대로 사용하며 봉투가 이를 대체하지 않는다.

검증 문장: 임의의 활성 API를 호출했을 때 성공·실패 응답 본문의 최상위 키 집합이 위 정의와 정확히 일치하고, 오류 코드 문자열이 `contracts/API.md`에 적힌 값과 일치한다.

## 변경 근거

- `S15P11B104-114`의 4개 인증 API(`API-AUTH-001`, `API-AUTH-002`, `API-AUTH-003`, `API-AUTH-005`)를 구현하려면 응답 본문을 직렬화해야 하므로 봉투 형식을 정하지 않고는 구현을 완료할 수 없다.
- `API-AUTH-002`는 `409 LOGIN_ID_DUPLICATED`, `API-AUTH-003`은 `401 INVALID_CREDENTIALS`를 반환해야 한다. 오류 코드 문자열을 클라이언트에 전달할 필드가 정의되어 있지 않으면 계약에 적힌 오류를 구현할 수 없다.
- 형식 미정의 상태에서 각 구현자가 임의로 정하면 React Native 클라이언트가 API별로 다른 파싱 로직을 갖게 되어, `contracts/API.md`가 금지하는 "임의로 만들지 않는다"는 조건이 사실상 개별 구현에 위임된다.
- 2026-07-28 사용자(백엔드 담당)가 평면 응답과 `data` 봉투 중 `{success, data, error}` 봉투 도입을 선택했다. 이 선택은 백엔드 구현 방향에 대한 결정이며, 프론트엔드와의 합의는 확인 필요다.

## 확인된 영향

- 영향 도메인: 계정·프로필(현재 구현 중), 이후 전체 도메인의 모든 API 응답
- 영향 계약: `contracts/API.md` 활성 API 59건 전체의 성공·오류 응답 본문. Method, Path, 상태 코드, 성공 결과 필드 자체는 변경하지 않는다.
- 영향 화면: 확인 필요. React Native 클라이언트의 모든 API 호출 응답 파싱이 이 형식에 의존한다.
- 검증 범위: 인증 API 4건의 성공·오류 응답 본문 통합 테스트. 나머지 API는 각 구현 시점에 동일 형식 적용 여부를 확인해야 한다.

## 확인이 필요한 질문

- 프론트엔드 담당자가 `{success, data, error}` 형식에 동의하는가. 이미 다른 형식을 전제로 클라이언트 API 계층을 작성했다면 조정이 필요하다.
- `error.message`를 클라이언트가 사용자에게 그대로 노출할 수 있는 문구로 볼 것인지, 개발자용 설명으로 볼 것인지.
- 검증 실패(`400 INVALID_REQUEST`)에서 어떤 필드가 잘못되었는지 전달할 필드(예: `error.details`)가 필요한지. 현재 제안에는 포함하지 않았다.
- `204 No Content`에 봉투를 포함하지 않는 규칙이 클라이언트 파싱과 충돌하지 않는지.
