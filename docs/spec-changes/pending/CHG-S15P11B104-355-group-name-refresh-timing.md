# 그룹명 변경의 전파 방식과 화면 갱신 시점 확정

- 상태: 제안
- 제안자: 이경호
- 작성일: 2026-08-07
- 차단 변경: 아니오
- 영향 스펙·계약: `domains/GROUPS_AND_MEMBERSHIP.md` 「확정된 동작」과 「구현 규칙 · 화면」, `contracts/API.md` `API-GROUPS-006`
- 관련 작업: S15P11B104-355

## 기존 내용

`docs/specs/domains/GROUPS_AND_MEMBERSHIP.md`의 「확정된 동작」에는 **그룹명 변경 자체를 규정하는 항목이 없다.** 그룹 생성·전환·역할 변경·탈퇴·삭제는 있으나 이름 수정 동작과 그 전파는 목록에 없고, 「미결정 사항」에도 올라가 있지 않다.

같은 문서의 역할 변경 규정은 "변경된 권한은 즉시 적용하고 대상 사용자에게 결과를 표시한다"로 시점을 명시하는데, 그룹명 변경에는 대응하는 문장이 없다.

`docs/specs/contracts/API.md`의 `API-GROUPS-006`은 성공 결과를 `id`, `name`, `updatedAt`으로만 정의하고 전파 규정이 없다. `docs/specs/domains/NOTIFICATIONS.md`에도 그룹 변경 이벤트 타입이 없다.

즉 **그룹명을 바꾼 뒤 다른 구성원 화면에 언제 새 이름이 보여야 하는지가 정의되어 있지 않다.**

## 제안 내용

**1. 전파 방식.** 서버는 그룹명 변경을 다른 구성원에게 능동 전파하지 않는다. `API-GROUPS-006`은 알림을 만들지 않고 푸시를 보내지 않으며 응답 계약도 바꾸지 않는다. 각 클라이언트는 자신이 수행하는 그룹 조회 결과로만 새 이름을 알게 된다.

**2. 변경한 사용자.** `API-GROUPS-006`이 `200`으로 응답하면 클라이언트는 **응답의 `name`**을 표시 값으로 즉시 반영한다. 사용자가 입력한 문자열이 아니라 응답 값을 쓴다. 서버가 앞뒤 공백을 정리하므로 두 값이 다를 수 있다.

**3. 다른 구성원의 갱신 시점.** 다른 구성원의 클라이언트는 다음 네 시점 중 하나가 완료된 직후의 화면부터 새 이름을 표시한다. 이 목록 밖의 시점에는 갱신을 보장하지 않는다.

- 로그인 성공 또는 저장된 세션 복원 완료 (`API-GROUPS-001` 반영 시점)
- 앱이 백그라운드에서 포그라운드로 복귀 (`API-GROUPS-001` 재조회 반영 시점)
- 그룹정보 탭 진입 (`API-GROUPS-004` 반영 시점)
- 그룹 범위 요청의 `403` 수신에 따른 그룹 목록 재확인 (`API-GROUPS-001` 반영 시점)

**4. 화면 간 일관성.** 표시용 그룹명은 클라이언트에서 하나의 상태로만 보관한다. 위 시점 중 하나가 완료되면 그룹명을 표시하는 모든 지점이 같은 값을 보인다. 앱 셸 헤더의 그룹 전환 트리거, 그룹 전환 시트 항목, 게시글 상세 헤더, 그룹 나가기 요약, 그룹 삭제 확인, 그룹명 변경 초기값이 대상이다. **한 화면은 새 이름을, 다른 화면은 옛 이름을 보이는 구간을 허용하지 않는다.** `API-GROUPS-004`가 돌려준 이름은 이 단일 상태를 갱신하는 입력이며 화면이 직접 읽는 표시 값이 아니다.

**5. `API-GROUPS-014`의 `confirmationName`.** 클라이언트는 4번의 단일 상태에 있는 그룹명을 그대로 보낸다. 관리자가 다른 기기에서 이름을 바꾸고 이 기기가 3번의 시점을 거치지 않았다면 `409 GROUP_NAME_MISMATCH`가 정상 응답이며, 클라이언트는 오류 문구로 표시한다. 자동 재조회·재시도는 하지 않는다.

## 변경 근거

- QA에서 "그룹명 변경 후 구성원마다 다른 시점에 새 이름이 보인다"가 보고됐다(S15P11B104-355). 원인은 같은 그룹명이 갱신 주기가 다른 두 클라이언트 상태에 이중화된 것이다. 그룹 목록 상태는 포그라운드 복귀 등에서만 갱신되고, 그룹 상세 상태는 그룹정보 탭 진입마다 갱신된다. 그래서 다른 구성원은 그룹정보 탭에서는 새 이름을, 셸 헤더와 게시글 상세 헤더에서는 옛 이름을 본다.
- 3번의 네 시점은 **모두 현재 구현에 이미 존재하는 트리거**다. 이 제안은 새 트리거를 추가하지 않고 현재 동작을 규정으로 승격시킨다. 새로 요구하는 것은 4번의 일관성뿐이며, 상세 응답의 이름을 목록 상태로 올려 표시 출처를 하나로 만드는 방식으로 충족했다. 추가 네트워크 호출은 없다.
- "탭 전환 일반"이나 주기적 폴링을 시점으로 넣지 않았다. 전자는 QA가 별건으로 묶으라고 권고한 전역 재조회 정책(F-13·F-15·F-18·F-22)에 속하고, 후자는 서버 호출 증가 대비 이득이 없다.
- 2번은 서버 정규화와 클라이언트 입력이 어긋나던 문제를 닫는다. 기존 구현은 그룹 목록에는 서버 값을, 그룹 상세에는 입력값을 넣어 두 값이 달라질 수 있었다.
- 구현과 검증 위치: `frontend/src/features/group-info/screens/GroupInfoScreen.tsx`의 `onGroupNameLoaded`와 `handleRenameGroup`, `frontend/App.tsx`의 `handleGroupNameLoaded`, `frontend/__tests__/App.test.tsx`의 "다른 구성원이 바꾼 그룹명은 그룹정보 진입 뒤 셸 헤더와 전환 시트에도 반영된다"·"그룹명 변경은 입력값이 아니라 서버가 돌려준 이름을 반영한다", `frontend/src/features/group-info/screens/GroupInfoScreen.test.tsx`의 상세 응답·늦은 응답·삭제 확인 테스트

## 확인된 영향

- 영향 도메인: 그룹·구성원의 그룹명 변경과 표시
- 영향 계약: `domains/GROUPS_AND_MEMBERSHIP.md`에 그룹명 변경 동작과 위 갱신 시점·일관성 규정을 추가한다. `contracts/API.md` `API-GROUPS-006`의 Method, Path, 요청·응답 필드와 오류는 **변경하지 않는다**. 서버 코드 변경도 없다.
- 영향 화면: 앱 셸 헤더와 그룹 전환 시트, 게시글 상세 헤더, 그룹정보와 그 하위 화면(나가기·삭제 확인·이름 변경)
- 검증 범위: 프론트 101 suites / 832 tests 통과, 타입 검사와 린트 무오류. 다른 구성원 시나리오는 "목록은 옛 이름, 상세는 새 이름, 이 기기는 변경을 호출한 적 없음"으로 재현했다.

## 확인이 필요한 질문

- 피드 탭에 머무는 동안 다른 구성원이 바꾼 이름이 보이지 않는 것을 제품이 수용하는가. 수용하면 3번 목록이 확정된다.
- 그룹명 변경을 알림으로 알릴 필요가 있는가. 이번 제안은 "필요 없다"로 두었다. 필요하다면 `NOTIFICATIONS.md`에 타입을 추가하는 별도 티켓이 된다.
