# AI 통화 AI 발화 중 끼어들기 차단과 마이크 게이팅 규정 추가

- 상태: 제안
- 제안자: 손수호
- 작성일: 2026-08-07
- 차단 변경: 아니오
- 영향 스펙·계약: `docs/specs/domains/AI_CALL.md`
- 관련 작업: S15P11B104-370

## 기존 내용

- `docs/specs/domains/AI_CALL.md`의 "AI 작업 컨텍스트" 포함 범위는 "페르소나 선택,
  세션 생성, WebRTC 연결, 실시간 자막, Tool Calling, 통화 상태·종료, 내부 저장
  경계"이며, 제외 범위는 "장기 기억(MVP 제외), 통화 녹음 재생, 보호자에게 전문
  제공, 확장 검색 Tool"이다. **통화 중 발화 턴 전환과 끼어들기는 포함 범위에도
  제외 범위에도 없다.**
- 같은 문서 "확정된 동작" 6번은 "통화 화면에는 통화 시간, 음소거, 통화 종료,
  스피커 제어와 AI 발화 실시간 자막을 제공한다"로, 제어의 **존재**만 규정한다.
  사용자가 AI 발화를 말로 끊을 수 있는지는 규정하지 않는다.
- 같은 문서 "확정된 동작" 7번은 "AI 발화 자막은 항상 표시한다. 사용자 발화 자막과
  자막 끄기 기능은 제공하지 않는다. 자막 delta는 화면 표시용이고, 완료된 발화 단위
  텍스트만 내부 처리와 리포트 생성에 사용한다"로, 자막과 전사 사용 범위만 규정한다.
- 같은 문서 `AC-002`는 `Given: 통화가 IN_PROGRESS다` / `When: AI가 발화하고 사용자가
  음소거·스피커·종료 제어를 사용한다` / `Then: AI 발화 자막은 항상 갱신되고 사용자
  발화 자막·자막 끄기 기능은 나타나지 않으며, 완료된 발화만 내부 transcript 처리에
  사용된다`이다. AI 발화 중 사용자가 **말로** 개입했을 때의 결과는 규정하지 않는다.
- 같은 문서 "미결정 사항"에도 끼어들기·턴 전환·VAD가 없어, 미결정으로 추적되는
  것조차 아닌 스펙 공백이다.
- `docs/specs/` 전체에 `끼어들기`, `barge-in`, `interrupt`, `VAD` 기술이 없다.
  `VAD`는 `docs/qa/two-user-emulator-qa.md`의 "AI는 먼저 말을 걸지 않으므로(server
  VAD) 연결 후 사용자가 발화해야 대화가 시작된다"에만 등장하며, 이는 QA 실행 메모이고
  공식 스펙이 아니다.
- `docs/specs/contracts/DATA_MODEL.md`의 `call_transcripts`는 "사용자와 AI의 전사
  완료 이벤트를 발화 단위로 저장한다. 실시간 `delta`는 자막에 쓸 수 있지만 영구 저장
  기준이 아니다"로 규정한다. 수집 대상에 시간대 조건은 없다.

## 제안 내용

`docs/specs/domains/AI_CALL.md`의 "확정된 동작"에 다음을 추가한다. 항 번호는 반영
시점에 결정한다.

1. AI 발화 음성이 재생되는 동안 단말은 마이크 입력을 전송하지 않는다. 이 구간에
   사용자가 말해도 AI 발화는 중단되지 않고 끝까지 재생된다.
2. 이 구간의 사용자 발화는 서버로 전달되지 않으므로 AI 응답에 반영되지 않고
   `call_transcripts`에도 저장되지 않는다. 사용자는 AI 발화가 끝난 뒤에 말한다.
3. 이 자동 차단은 사용자의 음소거 조작과 독립적인 계층이다. 음소거 제어의 표시
   상태는 사용자 조작만 반영하며, 자동 차단이 해제될 때 사용자가 켠 음소거는
   유지된다. 자동 차단 중 사용자가 음소거를 해제하면 AI 발화가 끝난 뒤에 반영된다.
4. AI 발화 재생 종료 신호가 도착하지 않거나 통화 연결이 끊긴 경우에도 마이크 차단이
   지속되지 않는다. 차단 해제 조건이 불확실하면 항상 마이크가 열린 상태로 수렴한다.
5. 자동 차단 상태는 통화 화면에 별도로 표시하지 않는다.

`AC-002`와 별개로 다음 인수 조건을 추가한다. 번호는 반영 시점에 결정한다.

- Given: 통화가 `IN_PROGRESS`이고 AI 발화 음성이 재생되고 있다.
- When: 사용자가 말을 시작한다.
- Then: AI 발화 음성과 자막이 끝까지 유지되고, 그 구간의 사용자 발화는 `transcript`에
  나타나지 않으며, AI 발화가 끝난 뒤의 사용자 발화는 정상적으로 인식된다.

## 변경 근거

- 끼어들기를 차단하는 결정은 팀이 내렸다. 통화 대상이 어르신이라 AI 발화가 중간에
  끊기는 경험이 민감하다는 이유다. 자동 차단 상태를 화면에 표시하지 않는 결정도
  같은 논의에서 내렸다.
- 현재 동작은 실제 통화 이벤트 로그로 확인했다. AI 발화 중 사용자가 말했을 때
  `response.done` → `input_audio_buffer.speech_started` →
  `output_audio_buffer.cleared` → `conversation.item.truncated` 순서가 관측되었고
  `response.cancelled`는 없었다.
- `response.cancelled`가 없다는 것은 서버 세션 설정의 `interrupt_response: false`가
  정상 적용되었다는 뜻이다. 이 설정은
  `backend/src/main/java/com/ssafy/s15p11b104/domain/call/service/OpenAiRealtimeGateway.java`의
  `createSessionJson`에서 `turn_detection`에 함께 전달되며,
  `backend/src/test/java/com/ssafy/s15p11b104/domain/call/service/OpenAiRealtimeGatewayTest.java`가
  이 JSON을 검증하고 있다.
- 음성을 끊는 주체는 응답 취소가 아니라 WebRTC 출력 오디오 버퍼 클리어다. OpenAI
  Realtime 공식 문서는 WebRTC·SIP 연결에서 서버가 출력 오디오 버퍼를 관리하며 사용자
  끼어들기가 발생하면 재생되지 않은 오디오를 자동으로 잘라낸다고 규정하고,
  `output_audio_buffer.cleared`를 "VAD 모드에서 사용자가 끼어들었을 때" 발생하는
  이벤트로 설명한다. 응답 생성은 재생보다 훨씬 빨리 끝나므로 사용자가 "AI가 말하는
  중"이라고 느끼는 시간 대부분은 이미 `response.done` 이후이며, 그 시점에는
  `interrupt_response`가 보호할 진행 중인 응답이 존재하지 않는다.
- 이 버퍼 클리어를 비활성화하는 세션 설정은 OpenAI API에 없다. 확인한 클라이언트
  이벤트는 클라이언트가 능동적으로 재생을 끊는 `output_audio_buffer.clear`뿐이다.
  따라서 서버 설정으로는 막을 수 없고, 단말이 마이크 입력을 차단해 서버 VAD가 사용자
  발화를 감지하지 못하게 하는 방법만 남는다.
- 구현 위치는 `frontend/android/app/src/main/java/com/s15p11b104app/aicall/AiCallWebRtc.kt`다.
  같은 파일의 `setMicrophoneEnabled`가 이미 `audioTrack.setEnabled`로 마이크 전송을
  제어하고 있어 차단 수단은 존재한다. 3번을 규정하는 근거는 이 단일 경로를 사용자
  음소거와 자동 차단이 공유하면 자동 차단 해제가 사용자 음소거를 풀어버린다는 점이다.
- 4번을 규정하는 근거는 실패 비용의 비대칭이다. AI 발화가 한 번 끊기는 것은 품질
  문제이지만 마이크가 계속 차단된 상태로 남으면 사용자가 말을 걸 수 없어 통화가
  사실상 종료된다. 돌봄 서비스에서 후자가 훨씬 치명적이므로 불확실한 상황은 모두
  마이크가 열리는 쪽으로 수렴시켜야 한다.
- 함께 기록할 결합: 끼어들기가 불가능해지므로 사용자에게 긴 발화를 벗어날 수단이
  없어진다. `backend/src/main/java/com/ssafy/s15p11b104/domain/call/service/AiCallPromptComposer.java`가
  응답을 "두 문장 이내, 한 문장 25자 안쪽, 소리 내어 읽을 때 약 10초"로 지정하고
  있는데, 이 목표가 이번 변경 이후 실질적인 하드 제약이 된다. 응답 길이가 길어지는
  회귀는 곧바로 체감 품질 저하로 이어진다. 이 목표는 `CHG-S15P11B104-300-ai-call-response-length.md`가
  다루는 범위이므로 함께 검토한다.
- 트레이드오프는 명확하다. AI 발화 중 사용자 발언이 무시되므로, 어르신이 AI 말
  중간에 대답하면 AI가 듣지 못한 것처럼 동작한다. 팀은 음성이 끊기는 것보다 이쪽이
  낫다고 판단했다.

## 확인된 영향

- 영향 도메인: `AI_CALL`. 다른 도메인 규칙은 바뀌지 않는다.
- 영향 계약: 없다고 판단한다. `contracts/API.md`의 `API-CALLS-001`~`API-CALLS-003`에
  오디오·턴 전환 설정 파라미터가 없으므로 API 계약은 변경되지 않는다.
  `contracts/DATA_MODEL.md`의 `call_transcripts` 스키마와 저장 규칙도 변경되지
  않는다. 게이팅 구간에는 사용자 전사 완료 이벤트 자체가 발생하지 않으므로 "전사
  완료 이벤트를 발화 단위로 저장한다"는 규정을 위반하지 않는다. 다만 그 문장을 읽는
  사람이 기대하는 수집 범위가 시간축으로 좁아지는 것은 사실이므로 아래 질문에 남긴다.
- 영향 화면: IA `F-2` 통화 중 화면. 5번에 따라 표시 변경은 없다.
- 검증 범위: `:app:testDebugUnitTest`, `:app:connectedDebugAndroidTest`, 그리고
  에뮬레이터 또는 실기기에서 (1) AI 발화 중 사용자가 말해도 음성이 끊기지 않음,
  (2) AI 발화 종료 후 사용자 발화가 정상 인식됨, (3) 음소거 버튼이 사용자 조작만
  반영함, (4) 연결 단절·재연결 후에도 마이크가 살아 있음을 수동 확인한다. 실제 오디오
  경로는 계기 테스트로 검증할 수 없어 수동 확인이 필요하다.
- 커버리지 갱신 후보: `docs/specs/COVERAGE.md`의 `REQ-011 AI 통화 제어` 행. 현재
  비고 칸이 비어 있다. 확인 필요.
- 관련 제안: `CHG-S15P11B104-310-call-control-default-state.md`(통화 제어 기본 상태와
  조작 가능 단계, 아래 질문에서 충돌 지점 명시), `CHG-S15P11B104-300-ai-call-response-length.md`(응답
  길이와 턴 구성).

## 확인이 필요한 질문

- `CHG-S15P11B104-310-call-control-default-state.md`가 `AC-002`의 `Then`에 추가하려는
  "음소거와 스피커 제어의 조작 결과는 실제 마이크 전송과 오디오 출력 경로에 즉시
  반영된다"와 이 제안의 3번이 충돌한다. 자동 차단 중에는 음소거 해제가 즉시 마이크
  전송으로 이어지지 않고 AI 발화 종료 후에 반영된다. 두 제안이 함께 승인되면 그
  문장을 "AI 발화 중 자동 차단 구간을 제외하고 즉시 반영된다"로 조정할지 확인 필요.
  두 제안의 승인 순서에 따라 조정 대상 문서가 달라진다.
- `contracts/DATA_MODEL.md`의 `call_transcripts` 수집 범위가 시간축으로 좁아지는 것을
  공용 데이터 계약 변경으로 볼지 확인 필요. 이 제안은 이벤트 자체가 발생하지 않는
  것이므로 계약 변경이 아니라고 판단했으나, 팀이 계약 변경으로 판정하면 `차단 변경`
  으로 재분류하고 승인 전 구현을 중단해야 한다.
- `output_audio_buffer.started`와 `output_audio_buffer.stopped`가 실제로 단말 데이터
  채널에 도착하는지 확인 필요. 현재 로그로 확인된 것은 `output_audio_buffer.cleared`
  뿐이다. `started`가 도착하지 않으면 재생 시작을 알 수 없어 이 제안의 1번을 구현할
  대체 신호를 결정해야 한다. 구현 착수 시 logcat으로 먼저 확인한다.
