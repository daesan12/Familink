# 스펙 변경 제안

공식 스펙을 직접 수정하기 전에 변경 내용을 기록하고 합의하기 위한 공간입니다.
공식 스펙은 [`../specs/`](../specs/)에서 관리합니다.

## 폴더 구조

```text
spec-changes/
├─ pending/   # 검토 또는 반영을 기다리는 변경
├─ applied/   # 공식 스펙에 반영된 변경
└─ TEMPLATE.md
```

## 작성 규칙

- 변경 한 건마다 Markdown 파일 하나를 추가합니다.
- 처음에는 `pending/`에 작성합니다.
- 여러 팀원이 함께 쓰는 중앙 순번은 사용하지 않습니다.
- Jira 작업이 있으면 `CHG-B104-123-call-timeout.md`처럼 작성합니다.
- Jira 작업이 없으면 `CHG-20260727-kim-call-timeout.md`처럼 날짜와 작성자를 넣습니다.
- `제안` 상태의 내용은 아직 공식 개발 기준이 아닙니다.
- API, DB, 인증·권한 또는 다른 팀원의 작업을 막는 변경은 다음 날까지 기다리지 않고 바로 팀에 공유합니다.
- 최신 확정 원본을 최초 로컬 스펙으로 그대로 이관하는 작업은 변경
  제안으로 만들지 않습니다.
- 미결정 사항은 관련 공식 도메인 스펙에 미결정으로 남기며, 제안 작성자가
  임의로 확정하지 않습니다.

## 반영 절차

1. 공식 스펙과 목표 동작의 차이를 발견합니다.
2. `$spec-change-recorder`로 `pending/` 변경 제안을 생성하거나 보강합니다.
3. 팀이 제안을 승인, 보류 또는 반려합니다.
4. 명시적으로 승인된 범위만 `$spec-change-applier`로 공식 스펙에 반영합니다.
5. 관련 도메인·계약·UI와 `COVERAGE.md`를 확인합니다.
6. 작업 라우팅이 달라졌을 때만 `INDEX.md`를 수정합니다.
7. 변경 문서를 다시 읽어 검증한 뒤, 전체 처리가 끝난 제안을
   `applied/`로 이동합니다.

일부만 승인되어 나머지 범위의 처분이 끝나지 않은 제안은 `pending/`에
남겨 승인 범위를 잃지 않습니다.

## pending 제안 최소 조건

- 영향받는 스펙 ID 또는 문서가 적혀 있습니다.
- 기존 내용과 제안 내용이 구분되어 있습니다.
- 변경 근거와 확인된 영향이 적혀 있습니다.
- 승인 전에는 결정, 결정자, 결정일, 반영 문서와 반영 커밋을 비워 둡니다.

## 적용 완료 조건

- 승인된 범위와 실제 반영 문서를 확인할 수 있습니다.
- 반영 커밋은 실제 커밋이 확인된 경우에만 적습니다.
